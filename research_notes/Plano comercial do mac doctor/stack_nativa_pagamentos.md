## 1. UI framework: SwiftUI vs AppKit vs hybrid; alternatives (Tauri, Electron, Flutter, Kotlin/Compose Multiplatform); minimum macOS version; Liquid Glass

### Takeaway
The evidence converges on a hybrid: SwiftUI for app structure, forms, settings, inspectors and detail panes, with AppKit (`NSTableView`/`NSOutlineView` via `NSViewRepresentable`) for any list/table that can exceed a few thousand rows or needs full Mac behaviours (context-menu targeting, drag sources, keyboard handling). Native Swift is roughly an order of magnitude lighter than Electron in RAM, launch time and bundle size; Tauri is close to native in size but not in RAM once WebKit helper processes are counted, and every non-native option still needs Swift/ObjC code for XPC, `SMAppService` and other privileged APIs. A deployment target of macOS 14 or 15 covers roughly 95%+ of the observed (indie/developer-skewed) installed base; Liquid Glass is no longer optional once you build with the Xcode 27 SDK.

### Cited Findings

**SwiftUI vs AppKit: large lists/tables (measured)**
- MEASURED (VENDOR/project blog, M1 MacBook Pro 16 GB, macOS 15, Instruments): SwiftUI `List` fast-scroll: 5,000 rows 58 FPS / ~120 MB; 10,000 rows 45 FPS / ~220 MB; 50,000 rows 31 FPS / ~540 MB; 100,000 rows 22 FPS / ~800 MB. `LazyVStack` in `ScrollView` at 100k rows: >1.2 GB and <20 FPS. `NSTableView` at 100,000 rows: 45 MB and constant 60 FPS, ~50 live `NSView`s. — [Rockxy, "Virtual-Scrolling 100k Network Requests in SwiftUI", 21 Mar 2026](https://rockxy.io/blog/virtual-scrolling-swiftui)
- MEASURED (same source): inserting rows at 500 events/s without batching = 100% main-thread CPU and UI freezes; with 100 ms batching = 4% main-thread CPU, 60 FPS. Time to first row visible <16 ms. — [Rockxy](https://rockxy.io/blog/virtual-scrolling-swiftui)
- Same source's stated trade-offs of going AppKit for the list: no SwiftUI animations, imperative column code, explicit accessibility wiring ("took an extra day"), two paradigms in one app. Its conclusion: SwiftUI "is the right choice for most of Rockxy's UI. Detail views, forms, inspector panels, popovers, settings windows", but "log viewers, network monitors, database browsers, file managers, analytics dashboards... will hit the wall"; "`NSTableView` via `NSViewRepresentable` is still the right answer in 2026." — [Rockxy](https://rockxy.io/blog/virtual-scrolling-swiftui)
- The Rockxy post claims `List` on macOS is backed by `NSCollectionView`; another 2026 post says `List` "inherits the behavior from `NSTableView`". The two sources conflict on the backing implementation; I did not resolve this. — [Rockxy](https://rockxy.io/blog/virtual-scrolling-swiftui); contradicted by [Paulo Andrade, "Using SwiftUI to Build a Mac-assed App in 2026", 6 May 2026](https://pfandrade.me/blog/mac-assed-swiftui-app/)
- OPINION: `LazyVGrid` does not recycle views like `NSCollectionView`; "at tens of thousands of items that produces noticeable stuttering"; "For a new macOS application that is NOT displaying a library of 100,000 items, SwiftUI is the reasonable default"; mixing both frameworks "is a normal and supported approach." — [DigitalBlake, 28 Apr 2026](https://digitalblake.com/2026/04/28/swiftui-vs-appkit-macos-ui-performance/)
- Apple claimed 6x (loading) and 16x (updating) list improvements at WWDC 2025; Michael Tsai's commentary: these "don't seem like enough to match `NSTableView`. The session cites improved scheduling and lazy loading rather than an architectural change." A quoted developer notes `List` requires a pre-existing `Collection` (no lazy data loading) and no fixed-row-height fast path. — [Michael Tsai, "SwiftUI at WWDC 2025", 18 Jun 2025](https://mjtsai.com/blog/2025/06/18/swiftui-at-wwdc-2025/)
- MEASURED (single app, Instruments): a calendar app recorded main-thread hangs of 438 ms (99% main-thread coverage) and 355 ms (100%), all attributed to SwiftUI updates/layout; hover effects over tens-to-hundreds of tiles were the trigger. The developer moved week/day/month grids to CoreGraphics drawing in a few `NSView`s on 2 Nov 2026 (shipped in v3.0), keeping SwiftUI for scrolling. OPINION from the same post: "The 80% of time you save on SwiftUI, you give back in the last 20%." — [hora Calendar, "AppKit vs SwiftUI: Why hora Left SwiftUI", Nov 2026](https://horacal.app/blog/swiftui-vs-appkit/)

**SwiftUI pain points specific to "Mac-assed" apps (opinion, experienced Mac developer)**
- No way in SwiftUI to know whether a context menu is open, so correct right-click targeting outside `List` is "impossible"; `List` gives correct behaviour but "is incredibly hard to customize" (changing selection colour can break the fade animation); three generations of drag-and-drop API and still no drag-source visibility comparable to `NSDraggingSource`; a focused `TextField` swallows key events so Spotlight-style "type while arrowing through results" is "currently not possible in pure SwiftUI". — [Paulo Andrade, 6 May 2026](https://pfandrade.me/blog/mac-assed-swiftui-app/)
- Catalyst on Tahoe: quoted developer reports crashes and layout glitches five months after release and sees "no option other than build an entirely new SwiftUI-native Mac App". — [Michael Tsai, "Catalyst in Tahoe", 19 Mar 2026](https://mjtsai.com/blog/2026/03/19/catalyst-in-tahoe/)

**Liquid Glass / current design language**
- Apps using standard SwiftUI/AppKit components pick up Liquid Glass automatically when built with the latest SDK; Apple advises using custom glass sparingly, grouping custom glass in a `GlassEffectContainer` for rendering performance, and performance-testing after adoption. `UIDesignRequiresCompatibility` is offered as a temporary opt-out. — [Apple, "Adopting Liquid Glass"](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass.md)
- Apple's documentation for `UIDesignRequiresCompatibility` now states the system ignores the key when building for OS 27 or later; Xcode 27 shipped 14 Sep 2026, so the opt-out lasts only while a team keeps building with Xcode 26. (Article quotes Apple docs; written about iOS but the key is cross-platform.) — [Carlos Lastres, 3 Nov 2026](https://lastres.ai/blog/liquid-glass-opt-out-ends-ios-27/); consistent with [meniscus.site SwiftUI recipe](https://meniscus.site/liquid-glass/swiftui)
- `.glassEffect`, `GlassEffectContainer` and glass button styles require macOS 26; on earlier systems you need a fallback material. — [meniscus.site](https://meniscus.site/liquid-glass/swiftui)
- macOS 27 changes picked up automatically: sidebars extend to the window edges, sidebar selection uses semibold text, bordered toolbar items over the sidebar adopt glass, the automatic scroll-edge effect resolves to a hard edge under free-floating title text; a new interactive "bounce" glass effect exists for controls. — [Apple, WWDC26 session 289 "Modernize your AppKit app"](https://developer.apple.com/videos/play/wwdc2026/289/)
- Early-beta era bugs in the AppKit glass implementation were documented (e.g. scroll-edge effects not applied to `NSScrollView` unless `hasVerticalScroller` is true, Tahoe beta 7). — [Jon Sterling weeknotes 2025-W34](https://www.jonmsterling.com/2025-W34/)

**Notarization / signing complexity of the alternatives**
- Tauri: Developer ID + notarization via App Store Connect API key or Apple ID env vars; built into `tauri build`. — [Tauri macOS code signing](https://v2.tauri.app/distribute/sign/macos/)
- Practitioner guides say Tauri apps need the hardened-runtime exceptions `com.apple.security.cs.allow-jit` and `allow-unsigned-executable-memory` (one adds `allow-dyld-environment-variables`) for the WebView, and that unsigned sidecar binaries make notarization fail. — [dev.to/0xmassi, 9 Feb 2026](https://dev.to/0xmassi/shipping-a-production-macos-app-with-tauri-20-code-signing-notarization-and-homebrew-mc3), [techXcelerate Tauri docs](https://techxcelerate.ntxm.org/docs/tauri/building--distribution/code-signing/macos-code-signing/)
- Electron: hardened runtime with `com.apple.security.cs.allow-jit` (Electron 12+; older versions also needed `allow-unsigned-executable-memory`, which "increases your app's attack surface"). — [electron/notarize README](https://github.com/electron/notarize?tab=readme-ov-file)
- Electron native modules must be compiled for Electron's Node ABI, producing two builds of the same driver (test vs app). — [Corey Daley](https://coreydaley.dev/posts/2026/11/native-apple-apps-vs-electron/)

### Inferences
- For a diagnostic tool whose core screens are process lists, file findings, launch items and logs, plan the main tables as AppKit from day one; the measured SwiftUI `List` degradation starts around 10k rows, which a filesystem or log scan can exceed easily.
- A security product that ships a web UI must carry JIT-related hardened-runtime exceptions (Tauri/Electron); a native Swift app can ship with no such exceptions. That is a defensible marketing and audit point for a security tool, in addition to the 5-10x RAM and launch-time gap.
- None of the cross-platform options removes Swift work for this product: the root helper, XPC, `SMAppService`, code-signing requirement checks and Sparkle are all Apple-framework code. Cross-platform UI would add a second toolchain without removing the first.
- Deployment target: macOS 14 minimum loses roughly 8% in the least-updated dataset found (JUCE vendor: 13 and older ≈ 8.2%) and ~1-3% in indie-skewed panels; macOS 15 minimum loses a further ~9% in that same dataset. macOS 13 is the hard floor imposed by `SMAppService`. Since Liquid Glass APIs are 26+, any target below 26 requires `if #available` fallbacks for custom glass.
- Building with Xcode 27 means the app gets the glass design on 26/27 regardless; design the UI with standard toolbars/sidebars so the system does the work, and keep custom glass minimal in data-dense views (Apple's own guidance).

### Gaps
- No general-population macOS version share exists (StatCounter is broken for macOS; TelemetryDeck, Homebrew and one plugin vendor are all skewed samples). No Brazil-specific macOS version data found.
- No independent benchmark of SwiftUI `Table` (as opposed to `List`) on macOS 26/27 was found; whether Apple's WWDC25/26 list improvements changed the 10k+ row picture is unverified beyond Tsai's scepticism.
- I did not find engineering posts from Panic, Rogue Amoeba, Raycast or MacPaw dated 2025-2026 on their UI stack choice; none are cited.
- Several benchmark sources are vendors or single runs; only Nucleus, Better Stack and Corey Daley state a method.
- Reported Liquid Glass rendering-performance cost on older Macs was not quantified by any source found.

## 2. Language and concurrency: Swift 6 strict concurrency, actors, async XPC, Swift Testing, Instruments; reliability practices for a privileged daemon

### Takeaway
Swift 6.2's "approachable concurrency" (main-actor default isolation plus caller-inherits-isolation async functions) is the default for new Xcode 26/27 app targets and fits a UI app; library/daemon modules should stay nonisolated with explicit actors. For the root helper, the current pattern is an `SMAppService` daemon bundled in the app, an XPC interface locked with `setCodeSigningRequirement`, strict input validation, and a versioned handshake so app and helper can be at different versions during updates.

### Cited Findings

**Swift 6.x**
- Swift 6.2 (15 Sep 2025) introduced: opt-in main-actor-by-default isolation ("ideal for scripts, UI code, and other executable targets"), async functions that run in the caller's context (upcoming feature), and `@concurrent` to explicitly offload work. — [Swift.org, Swift 6.2 Released](https://www.swift.org/blog/swift-6.2-released/); [WWDC25 "What's new in Swift"](https://developer.apple.com/videos/play/wwdc2025/245/)
- Build settings: `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (SE-0466) and `SWIFT_APPROACHABLE_CONCURRENCY = YES` (enables `NonisolatedNonsendingByDefault`/SE-0461 and four other upcoming features). Xcode 26 turned both on for new projects and Xcode 27 (Swift 6.4) keeps them. Bare Swift 6 language mode still runs nonisolated async functions on the global executor unless the flag is set. In packages: `.defaultIsolation(MainActor.self)` plus `.enableUpcomingFeature("NonisolatedNonsendingByDefault")`. — [Blake Crosley, 3 Jun 2026](https://blakecrosley.com/blog/swift-6-2-concurrency-in-practice)
- OPINION (same source): do not default-isolate a non-UI library target ("a networking layer, a parser, or a data engine") to the main actor. — [Blake Crosley](https://blakecrosley.com/blog/swift-6-2-concurrency-in-practice)
- Swift 6.4 (15 Sep 2026): Swift Build is the default in SwiftPM; `Subprocess` reaches 1.0 ("a stable, cross-platform way to run and interact with other programs"); `XCTAssert` usable inside Swift Testing tests and `#expect` inside XCTests (ST-0021); `swift test` can repeat test cases. — [Swift.org, Swift 6.4 Released](https://www.swift.org/blog/swift-6.4-released/)
- Swift Testing: exit tests (verify `precondition`/`fatalError` paths in a child process) and attachments since 6.2; issue severity (warnings that do not fail CI) in 6.4; parameterized tests run in parallel by default. — [Swift.org 6.2](https://www.swift.org/blog/swift-6.2-released/), [WWDC26 "What's new in Swift"](https://developer.apple.com/videos/play/wwdc2026/262/), [WWDC26 "Migrate to Swift Testing"](https://developer.apple.com/videos/play/wwdc2026/267/)

**Instruments (Xcode 26)**
- New-generation SwiftUI instrument records the duration of every SwiftUI update and why each view body ran (Cause & Effect Graph); new Processor Trace, CPU Counters "bottleneck analysis", Power Profiler; Swift Concurrency template shows task names (Swift 6.2 API); the target chooser can filter to launch agents and daemons; `xctrace record` supports named runs. — [Xcode 26 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes.md)
- Xcode 26 testing: runtime-issue detection during tests, configurable to fail the test plan. — [Xcode 26 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes.md)

**Privileged helper: registration**
- `SMAppService` (macOS 13+) replaces `SMJobBless`/manual plists: daemon plist lives in `Contents/Library/LaunchDaemons` inside the app bundle and uses `BundleProgram` (bundle-relative path). A LaunchDaemon is not bootstrapped until an admin approves it in System Settings; approved daemons bootstrap on every boot. — [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice.md), [Apple register()](https://developer.apple.com/documentation/servicemanagement/smappservice/register().md), [Apple "Updating helper executables from earlier versions of macOS"](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos.md)
- Apple header documentation (mirrored in the Rust bindings docs): apps using `SMAppService` must be code signed; "Apps that contain LaunchDaemons must be notarized"; for a daemon to start at boot the app must be reachable before login, so "it is recommended that the application bundle live in /Applications"; "If an app updates either the plist or the executable for a LaunchAgent or LaunchDaemon, the SMAppService must be re-registered or it may not launch. It is recommended to also call unregister before re-registering if the executable has been changed." `unregister` kills a running service without waiting for it to be reaped; the completion-handler variant fires after the process is killed, after which re-registering is safe. — [docs.rs objc2-service-management (Apple header text)](https://docs.rs/objc2-service-management/latest/x86_64-apple-darwin/objc2_service_management/struct.SMAppService.html)
- Apple: tell users what the helper is for; check authorization status at launch; call `openSystemSettingsLoginItems()` when not authorized; register daemons first because approving the daemon approves the bundle's other helpers. — [Apple, Updating helper executables](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos.md)
- Practitioner rules from an open-source app with this architecture: "`SMAppService.status == .enabled` means registered, not running"; do not call `SMAppService.status` in a hot path because it "does synchronous IPC... and can block for 10-30+ seconds under load"; the XPC protocol file must be identical in both targets (enforced by a CI test); the helper is the only process that writes to system paths. — [KeyPath architecture docs](https://malpern.github.io/KeyPath/architecture/xpc-architecture.html)
- OPINION: "ask if you truly need elevated permissions... If you don't, don't use a daemon"; if the app is sandboxed the helper must be too. — [Bryson Tyrrell, 28 Apr 2025 (>18mo)](https://dev.to/brysontyrrell/macos-apps-with-embedded-daemons-333a)

**Privileged helper: XPC hardening**
- `NSXPCConnection.setCodeSigningRequirement(_:)` (macOS 13+) enforces a requirement on the peer for every message; mismatching messages invalidate the connection; call before `resume()`. — [Apple docs](https://developer.apple.com/documentation/foundation/nsxpcconnection/setcodesigningrequirement(_:)?changes=_2%2C_2)
- PID-based client validation is a TOCTOU/PID-reuse hole ("the canonical weakness behind several historical privileged-helper CVEs"); fix is `setCodeSigningRequirement` or audit-token validation. A real project fixed exactly this in June 2026. — [narcotic-sh/modafinil issue #4](https://github.com/narcotic-sh/modafinil/issues/4)
- `SMAuthorizedClients` is an `SMJobBless`-era, install-time key; with `SMAppService` the daemon itself must authorize callers, otherwise "any local process that can find the Mach service can drive this daemon AS ROOT". — [macos-app-scaffold template](https://github.com/xueshiqiao/macos-app-scaffold/blob/main/skills/macos-app-scaffold-new/templates/daemon/HelperMain.swift); same point in [Sojourn ADR 0024](https://github.com/Bizarre-Industries/Sojourn/blob/main/docs/decisions/0024-mas-touch-id-privileged-helper.md)
- Production example (Teleport VNet): requirement = same signing identifier + same Team ID + Developer ID Application cert; when the listener rejects a client the daemon never sees the attempt and the client only sees "interrupted", so they log a pointer to Console.app; the client side gets a clear `NSXPCConnectionCodeSigningRequirementFailure`. — [gravitational/teleport PR #44639](https://github.com/gravitational/teleport/pull/44639)
- Helper-side practices documented by projects: typed arguments (IDs as `UInt64`, never strings), `Process` invoked with an argv array and never a shell string, hard subprocess timeouts, OSLog audit of every invocation, per-call `AuthorizationCopyRights` only for step-up operations. — [Sojourn ADR 0024](https://github.com/Bizarre-Industries/Sojourn/blob/main/docs/decisions/0024-mas-touch-id-privileged-helper.md); rate limiting of state-changing calls, input validation of every parameter, 0600 temp files, certificate-chain comparison beyond bundle-ID strings — [Rockxy security docs](https://github.com/RockxyApp/Rockxy/blob/main/docs/development/security.mdx)
- Versioning: include protocol version and build identity in an authenticated health exchange "so a stale helper cannot impersonate a compatible one"; use versioned data formats with atomic writes; "Do not unregister and re-register on every launch as a general update mechanism"; test matrix: fresh install, approval denied, later granted, disabled in System Settings, app moved, app updated while helper runs, downgrade, damaged signature, missing helper. — [Daniel Cosenza, 27 Aug 2026](https://danielcosenza.com/posts/mac-smappservice-login-items/)

### Inferences
- Structure: app target = main-actor default isolation; `Core`/`Scanner`/`HelperProtocol` packages = nonisolated with explicit actors and `Sendable` DTOs; the helper = a small command-line target with no UI isolation defaults.
- `NSXPCConnection` with `setCodeSigningRequirement` is the best-documented path; wrap its reply-block API in `async` functions (`withCheckedThrowingContinuation`) in one client type so the rest of the app is pure async/await.
- Swift 6.4's `Subprocess` 1.0 is the natural replacement for the prototype's Python `subprocess` calls to system tools (`codesign`, `spctl`, `launchctl`, `log`, `profiles`), inside the helper and with argv arrays.
- Swift Testing exit tests fit a helper whose input validation should trap on impossible states.
- The Apple header's "must be re-registered or it may not launch" and Cosenza's "don't re-register on every launch" reconcile to: re-register only when the handshake shows a helper build mismatch after an update.

### Gaps
- I did not retrieve Apple documentation or a Quinn "The Eskimo!" forum post for the low-level Swift `XPCSession`/`XPCListener` API with `Codable` messages (macOS 14+), nor any evidence on whether it supports peer code-signing requirements as cleanly as `NSXPCConnection`; "async XPC" is therefore covered only by inference.
- No authoritative list of current `SMAppService` bugs on macOS 26/27 was found; the 10-30 s `status` blocking claim comes from a single project's docs.
- No source found on Endpoint Security / System Extension entitlements, which a security diagnostic tool may want later (requires an Apple-granted entitlement).

## 3. AI coding agents with Swift/SwiftUI/Xcode, and project structure that makes them reliable

### Takeaway
By late 2026 agents write competent Swift and Xcode exposes itself over MCP; the remaining failure modes are tooling-shaped (hand-edited `project.pbxproj`, invented destinations, giant `xcodebuild` logs, silencing concurrency errors with `@unchecked Sendable`). The most agent-friendly layout is a thin app target plus local Swift packages (buildable with `swift build`/`swift test`), synchronized folders or a generated project so adding files never touches the project file, and explicit rules plus hooks in `CLAUDE.md`/`AGENTS.md`.

### Cited Findings
- Xcode 26.3 "introduces support for agentic coding... powered by coding agents from Anthropic and OpenAI" (Claude Agent, Codex) and "makes its capabilities available through the Model Context Protocol"; includes a permissions system for external agent tools. Known issue: denying agent access to a project in Desktop/Documents/Downloads cannot be reversed from the prompt (move the project elsewhere). — [Xcode 26.3 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_3-release-notes.md)
- Apple's MCP bridge is `xcrun mcpbridge` (requires a running Xcode; talks to it over XPC): ~20 tools in Xcode 26.3 including `BuildProject`, `GetBuildLog`, `RunSomeTests`, `XcodeListNavigatorIssues`, `DocumentationSearch`, `RenderPreview`, `ExecuteSnippet`. Apple had "not published standalone documentation for the MCP server as of May 2026". The community XcodeBuildMCP (v2.3.2, 82 tools) wraps `xcodebuild` headlessly and returns structured JSON errors; limitation noted: its build tool is not incremental-aware. — [Blake Crosley, "Two MCP Servers Made Claude Code an iOS Build System"](https://blakecrosley.com/blog/xcode-mcp-claude-code)
- Xcode 26.6 added Google Gemini and Agent Client Protocol support; on Xcode 27.2 Apple's MCP server lists 54 tools. Limits of the in-Xcode agent panel on 26.x per this author: no hooks, does not load `CLAUDE.md`, no subagents, no extra MCP servers. — [Blake Crosley, "Building iOS Apps with AI Agents" (dated Apr 2026, evidently updated since)](https://blakecrosley.com/guides/ios-agent-development)
- XcodeBuildMCP 2.0 added a CLI (tools callable from the terminal, reducing context load) and proxies Xcode's MCP bridge; OPINION from Peter Friese: the MCP form was "a bit slow" and agents "have a hard time figuring out how to use it", possibly from the context cost of a many-tool server. — [Not only Swift, issue 93](https://not-only-swift.kit.com/posts/agentic-coding-in-xcode-swift-concurrency-and-star-trek-control-panels-not-only-swift-issue-93)
- Failure modes on real Xcode projects (practitioner): the agent "edits `project.pbxproj` by hand, and one bad merge later the project won't open"; "invents simulator names, so every `xcodebuild` call fails"; "'fixes' Swift 6 strict concurrency errors with `@unchecked Sendable`"; approval prompts on every build. Mitigations: a `PreToolUse` hook that blocks pbxproj writes, exact build/test commands in `CLAUDE.md`, `xcodebuild -quiet` because "full xcodebuild logs are huge and waste context", an explicit ban on concurrency escape hatches and on `ObservableObject` in new code. — [Pavlos Simas, 13 Oct 2026](https://simaspavlos.medium.com/making-claude-code-safe-for-xcode-projects-4-changes-that-fixed-it-for-me-538ee83b29d8)
- Concurrency is "where AI-written Swift breaks most visibly" because rules changed between Swift 5.5 and 6.2 and "the agent cannot see which settings your target uses unless you tell it"; recommended: state language mode, default isolation and upcoming features per target in `CLAUDE.md`/`AGENTS.md`, build after every change, migrate one module or warning category per session. For packages the agent can run `swift build -Xswiftc -strict-concurrency=complete`. — [SwiftSkills guide](https://swiftskills.dev/guides/swift-concurrency-ai-agents)
- OPINION (consultancy): "Claude Opus 4.8 was the first model we used that handled Swift 6's strict concurrency reliably, and the new Claude 5 family has pushed further still"; the failure mode "has shifted from 'doesn't compile' to 'compiles, and needs the same review any pull request needs'." Xcode MCP gives agents structured targets/schemes/diagnostics and access to Apple documentation "which agents struggle to read on the open web". — [Instil, 20 Aug 2026](https://instil.co/blog/agentic-ios-development-in-practice-xcode-mcp-claude-and-faster-delivery)
- OPINION: "Native iOS is hard mode for AI coding — slow compiles, a closed Xcode toolchain, no browser hot-reload"; what helps is expert agent skills (SwiftUI, concurrency, Liquid Glass) plus XcodeBuildMCP so the agent builds, runs, screenshots and iterates itself. — [ios-ai-devkit README](https://github.com/andyleimc-source/ios-ai-devkit)
- A public skill pack lists "14 hallucinated or misnamed APIs that recur across blogs, skills, and LLM output" for Liquid Glass (e.g. `toolbarMinimizeBehavior` renamed at iOS 27 beta 4). — [liquid-glass-skills README](https://github.com/YordiLorenzo/liquid-glass-skills)

**Project structure**
- Xcode 16 buildable folders (`PBXFileSystemSynchronizedRootGroup`) record only the folder path, so adding/removing files does not change the project file; targets, build phases, package references and build settings still live in the pbxproj. — [iPucu Lab, 4 Oct 2026](https://ipucubilisim.com.tr/en/blog-tuist-spm-xcodeproj.html); [Tuist blog, 21 Mar 2025 (>18mo)](https://tuist.dev/blog/2025/03/21/git-conflicts)
- "Thin project plus local Swift packages": app project holds only app target, extensions, entitlements, signing; everything else in local packages; "You can validate without Xcode using `swift build` and `swift test`"; no third-party tool; limits: package targets cannot take an xcconfig. — [iPucu Lab](https://ipucubilisim.com.tr/en/blog-tuist-spm-xcodeproj.html)
- Tuist 4.62.0 added buildable-folder support explicitly for agents: "Coding assistants and agents can modify your codebase without triggering project regeneration"; Tuist ships agent skills. Tuist CLI is MIT/free; cache and insights are a hosted paid service; latest 4.207.1 (Oct 2026). — [Tuist best practices](https://tuist.dev/en/docs/guides/features/projects/best-practices), [Tuist changelog, 11 Aug 2025](https://tuist.dev/changelog/2025.08.11-buildable-folders), [faun.dev comparison](https://faun.dev/toolbox/tuist-vs-xcodegen/)
- XcodeGen: one YAML spec, MIT, no service; supports `syncedFolder`; latest 2.46.0 (Jul 2026); single-maintainer community project; OPINION that it is the choice when "you want to be able to walk away in two hours". Criticism: permissive YAML "lasagna" at scale. — [iPucu Lab](https://ipucubilisim.com.tr/en/blog-tuist-spm-xcodeproj.html), [faun.dev](https://faun.dev/toolbox/tuist-vs-xcodegen/), [Gabriel Liévano, 22 Mar 2025 (>18mo)](https://lievano.me/posts/from-bazel-to-xcodegen-to-tuist/)

### Inferences
- For a solo founder orchestrating agents: put scan engines, parsers, models, licensing and the XPC protocol in local Swift packages with Swift Testing suites runnable via `swift test` (fast, no Xcode, no simulator, CI-friendly), and keep the Xcode project to three thin targets (app, helper daemon, tests) using synchronized folders.
- A project generator is optional at this size. If one is wanted to keep the pbxproj out of agents' reach, XcodeGen's single YAML is the lower-commitment choice; Tuist's extra value (cache, selective tests) targets large teams.
- A macOS-only app avoids the simulator-name failure mode entirely (destination is `platform=macOS`), which removes one of the four documented agent failure classes.
- The privileged helper and signing/notarization are the parts agents cannot fully verify alone (admin approval dialogs, real Developer ID identity), so they need scripted, human-triggered release steps and a manual test matrix.

### Gaps
- No quantitative benchmark of agent success rates on Swift vs other languages was found; all evidence is practitioner opinion.
- No source specifically covers agents working on macOS apps with privileged helpers; guidance is extrapolated from iOS-centric posts.
- Apple's own MCP server documentation status after May 2026 was not checked.

## 4. Auto-update outside the App Store: Sparkle 2, privileged helper updates, release pipeline

### Takeaway
Sparkle 2 remains the standard: EdDSA (ed25519)-signed archives and optionally signed appcasts, automatic delta generation, sandbox support through bundled XPC services, and an isolated launchd-submitted installer. Sparkle deliberately does not manage your daemon; the app must detect a helper/app version mismatch itself and re-register. The pipeline is: archive with hardened runtime → Developer ID sign (helper first, then app) → `notarytool submit --wait` → `stapler staple` → `generate_appcast`.

### Cited Findings

**Sparkle 2 capabilities**
- Security recommendations: serve over HTTPS, Developer ID sign and notarize, and sign archives/deltas/packages with EdDSA. `generate_keys` stores the private key in the login Keychain and prints the public key for `SUPublicEDKey`; keep keys off the web host. — [Sparkle documentation](https://sparkle-project.org/documentation/)
- `generate_appcast` on a folder of archives produces the appcast, EdDSA signatures and `.delta` files; if the app sets `SURequireSignedFeed` it also signs the appcast and release notes; Markdown release notes supported "as of Sparkle 2.9 and macOS 12". — [Sparkle documentation](https://sparkle-project.org/documentation/)
- CI key handling: the `-s` flag (private key as CLI argument) is deprecated as insecure since 2.2.2; use the Keychain or pass the key on stdin with `--ed-key-file -`. — [Sparkle security and reliability](https://sparkle-project.org/documentation/security-and-reliability/)
- Delta updates: one `.delta` per source version; fall back to the full archive on failure with checksum verification; delta format 4 requires Sparkle 2.7 (preserves bundle creation date), format 3 requires 2.1. — [Sparkle delta updates](https://sparkle-project.org/documentation/delta-updates/)
- Other features: beta channels, phased rollouts, critical/major update marking, silent background install. — [Sparkle GitHub](https://github.com/sparkle-project/Sparkle/)
- Sandboxing: needs `SUEnableInstallerLauncherService` and two mach-lookup temporary-exception entitlements; the Downloader XPC service is only for apps without the network-client entitlement and has drawbacks (legacy WebView release notes). Bundled XPC services are ad-hoc signed and should be re-signed for distribution. — [Sparkle sandboxing](https://sparkle-project.org/documentation/sandboxing/)
- Architecture: Sparkle 2 replaced `AuthorizationExecuteWithPrivileges` with "an isolated privileged installer process" submitted to launchd; extraction, validation and installation happen in that one process; Sparkle's XPC services check that clients share the Team ID; updates without an EdDSA key are deprecated ("Apple's code signature checks are not intended for complete integrity"). — [Sparkle Security.md](https://github.com/sparkle-project/sparkle/blob/2.x/Documentation/Security.md), [Sparkle Installation.md](https://github.com/sparkle-project/sparkle/blob/2.x/Documentation/Installation.md)
- Security fix history relevant to a root-level product: 2.9.6 "fixes a local privilege escalation attack allowing removal/creation of files in daemons/CLI tools that run as root using Sparkle"; 2.7.3 fixed TCC-file access via the Downloader service and arbitrary package install via the Installer service; 2.6.4 fixed a signature-check bypass by payload replacement. — [Sparkle security and reliability](https://sparkle-project.org/documentation/security-and-reliability/)

**Updating an app that owns a daemon**
- Sparkle maintainer: "Sparkle is for updating apps... Launch agents and daemons associated with those apps are updated by the app through other means"; updating a bundle while in use is not supported; pkg updates "cannot be done silently and aren't generally recommended"; "this approach of using Sparkle is wrong. The user can manually update your application without Sparkle. So whatever you need to do needs to generally work in situations where Sparkle isn't used"; `updaterWillRelaunchApplication` is not called for install-on-quit without relaunch, and "there is not a delegate callback for every scenario an app update is installed." — [Sparkle discussion #2572, May 2024 (>18mo)](https://github.com/sparkle-project/Sparkle/discussions/2572), [Sparkle discussion #2423, Aug 2023 (>18mo)](https://github.com/sparkle-project/Sparkle/discussions/2423)
- A `KeepAlive` launchd job is relaunched as soon as Sparkle terminates it, breaking the install; the maintainer points to bundled helpers via `SMAppService`. — [Sparkle discussion #2423 (>18mo)](https://github.com/sparkle-project/Sparkle/discussions/2423)
- Apple: after the plist or executable of a registered daemon changes, the service "must be re-registered or it may not launch"; unregister first if the executable changed. — [Apple header text via docs.rs](https://docs.rs/objc2-service-management/latest/x86_64-apple-darwin/objc2_service_management/struct.SMAppService.html)

**Release pipeline**
- Pipeline stages used by current open-source Mac apps: `xcodebuild archive` (Release, hardened runtime) → `codesign` Developer ID + timestamp → `notarytool submit` → `stapler staple` → `generate_appcast` → upload zip + dmg + appcast. — [Quoin distribution docs](https://github.com/2389-research/Quoin/blob/main/docs/reference/distribution.md)
- Ordering with a helper: sign the helper first with `--options=runtime`, then re-sign the outer app; verify both with `spctl --assess`. — [Sojourn ADR 0024](https://github.com/Bizarre-Industries/Sojourn/blob/main/docs/decisions/0024-mas-touch-id-privileged-helper.md)
- Notarize the ZIP and DMG containers and staple the DMG; one project avoids stapling the `.app` after signing because it "adds Contents/CodeResources, which can trip strict signature validation after the app is copied into a disk image". — [Keyty Fastfile](https://github.com/keytyapp/Keyty/blob/9447819b/fastlane/Fastfile)
- Notarization in CI: App Store Connect API key (`--key`, `--key-id`, `--issuer`, `--wait`); a Team key can be revoked independently of a personal Apple ID; `--issuer` must be omitted for Individual keys or the service returns 401; `altool` notarization ended 1 Nov 2023. — [Amore help](https://amore.computer/help/github-actions/)
- DMG creation with `create-dmg` in a GitHub Actions workflow, then `notarytool submit --wait --timeout 15m`. — [onelake-explorer-macos release.yml](https://github.com/sdebruyn/onelake-explorer-macos/blob/17b828032dd75f681f77231cf435debfc7ef012e/.github/workflows/release.yml)
- Losing the Sparkle private key means shipped apps cannot verify new updates; leaking it lets an attacker sign updates users' apps will trust. — [Quoin distribution docs](https://github.com/2389-research/Quoin/blob/main/docs/reference/distribution.md)

### Inferences
- Design the update flow so the app, on every launch, does an XPC handshake with the helper (protocol version + build number); on mismatch, `unregister` (completion handler) then `register`. This works for Sparkle updates, manual drag-replace updates and Setapp-delivered updates alike, which is exactly the maintainer's point.
- Avoid `KeepAlive` on the daemon; let it be launched on demand by the Mach service so Sparkle's replacement of the bundle is not fighting launchd.
- Use Sparkle ≥ 2.9.6 given the root-related privilege-escalation fix, enable `SURequireSignedFeed`, and keep the EdDSA key in a secrets manager plus an offline backup.
- A plain `.app` in a DMG with an in-app `SMAppService` registration avoids pkg installers (which Sparkle cannot install silently).

### Gaps
- The latest Sparkle version as of Nov 2026 was not confirmed (2.9.6 is the newest entry in the security table retrieved).
- No first-hand write-up of Sparkle + `SMAppService` daemon update behaviour on macOS 26/27 was found (e.g. whether the Background Items notification re-fires after re-registering); the two Sparkle discussions are older than 18 months.
- Alternatives to Sparkle were not researched in depth; the only alternative surfaced is the hosted Sparkle-compatible service Amore, pricing not checked.

Lemon Squeezy's public licence API is unscoped, so the app must check `store_id`/`product_id` in the response or another merchant's key validates; Dodo's validate returns only `{ valid }`. — [capawesome revenue-sdk PR #5](https://github.com/capawesome-team/revenue-sdk/pull/5)
- Polar's licence endpoints authenticate with the key itself so a Mac app does not have to embed an API token. — [polarsource/polar issue #4800, Jan 2025 (>18mo)](https://github.com/polarsource/polar/issues/4800)
- VENDOR claim (licensing startup founder): Paddle Classic "with built-in license keys and the Mac licensing framework is being wound down, and Paddle Billing... doesn't generate license keys or handle Mac trials and licensing at all." — [Keylight blog, 4 May 2026](https://keylight.dev/blog/why-i-built-keylight/). Paddle's own help centre still carries only a 2020-era article about the v3→v4 Mac SDK. — [Paddle help](https://www.paddle.com/help/manage/sdk/what-happens-when-the-v3-mac-sdk-is-no-longer-updated)
- Gumroad is reported to offer "no license key management" by one comparison; the Keylight founder says Paddle, Gumroad and Lemon Squeezy "all advertise license keys". The two sources conflict on Gumroad. — [fintechspecs.com, 29 Oct 2026](https://fintechspecs.com/blog/best-merchant-of-record-platforms-digital-products/); contradicted by [Keylight blog](https://keylight.dev/blog/why-i-built-keylight/)

**Offline-tolerant licence validation**
- The design problem: an online-only check must either fail closed (offline paying customer locked out) or fail open (blocking the network bypasses it); the alternative is locally verifiable signed keys plus periodic re-check for revocation. — [Keylight blog (VENDOR)](https://keylight.dev/blog/why-i-built-keylight/)
- Keygen: signed/encrypted licence files with a TTL (default and recommended starting point 30 days); Ed25519 is the default and recommended scheme; hard-code account ID and public key in the app ("should not be stored in external files or in the environment"); on verification assert `issued` is not in the future (clock tampering) and `expiry` not passed; Keygen recommends licence files over immutable signed keys. — [Keygen offline licensing docs](https://keygen.sh/docs/api/cryptography/)
- Keygen pricing reported by a competitor as $49-299/month (unverified). — [Zamok (competitor)](https://zamok.bshk.app/)
- Reference Swift pattern (no dependencies): CryptoKit `Curve25519.Signing.PublicKey.isValidSignature` over a token with device ID, licence ID and expiry; IOKit hardware UUID; token cached on disk; when stale, re-verify online; if offline, keep working for a configurable `offlineDays` grace; remove the token if the server returns 404. Compiles in Swift 6 mode, macOS 12+. — [Keygate Swift guide (VENDOR)](https://keygate.app/docs/swift)
- Keylight Swift SDK: Ed25519-signed "leases" minted from payments on the developer's own Stripe account, offline verification, device limits, trials, refund revocation. — [keylight-swift](https://github.com/keylight-dev/keylight-swift), [Keylight licence keys](https://keylight.dev/features/license-keys/)

**Setapp as an additional channel**
- Membership model: 70% of each subscriber's fee is split among the developers whose apps that user opened in the billing period, weighted by price-tier multipliers (tiers 1-17, based on the app's price outside Setapp held for at least 3 months); plus a 20% partner fee for users the developer referred, for as long as they stay subscribed (up to 90%). Worked example in the docs: $9.99 user, three apps → $4.24 to a referring developer. Revenue for a new user appears with a ~2-2.5 month delay. — [Setapp membership revenue docs](https://docs.setapp.com/docs/setapp-membership-revenue), [Setapp Partner Program](https://docs.setapp.com/docs/about-partner-program)
- Single-app distribution on Setapp: developer keeps 85% of subscription sales and 75% of one-time purchases. — [Setapp marketplace overview](https://docs.setapp.com/docs/setapp-marketplace-overview), [Setapp developers page](https://setapp.com/developers)
- Setapp "provides... licensing, payments, and tax management"; minimum macOS 13.0; entry is by invitation or application with a quality review, then technical review and Setapp SDK integration; usage must be reported (about hourly at most) for revenue calculation. — [Setapp marketplace overview](https://docs.setapp.com/docs/setapp-marketplace-overview), [Setapp developers page](https://setapp.com/developers), [Setapp Vendor API](https://docs.setapp.com/docs/integrating-apps-using-vendor-api)

### Inferences
- Viable routes for a Brazil-based solo founder, in order of least setup: (a) Paddle as MoR from a Brazilian CPF/CNPJ, payouts in USD by SWIFT ($15 fee, plus Brazilian inbound FX costs) or to Payoneer/a Wise-style USD account, Pix on BRL prices, plus a separate licensing layer; (b) Dodo or Creem (cheaper, list Brazil, but young companies); (c) a US LLC via Stripe Atlas to unlock Stripe Managed Payments or Polar, at 6.7-8.9% and with US entity overhead; (d) Stripe Brazil directly for domestic BRL sales with Pix at 1.19% but no MoR and BRL-only settlement.
- Lemon Squeezy is a poor foundation for a new 2026 product for a Brazilian seller: PayPal-only payouts to Brazil and a stated migration path to a product that excludes Brazil.
- Because the best-fit MoR (Paddle Billing) has no licence keys, and because provider lock-in is the recurring warning, own the licence format: an Ed25519-signed licence file verified in-app with CryptoKit, issued by a small webhook service (or Keygen/Keylight/Keygate), with a 14-30 day re-validation TTL and an offline grace period. The same verification code can live in a Swift package shared by the app and the helper.
- A security product should not fail closed on licence checks for safety-relevant features; signed offline licences make that possible without opening a trivial bypass.
- Setapp's partner fee makes it additive rather than cannibalising if the site links Setapp with the partner badge; its SDK replaces the licensing layer in the Setapp build, so licensing should sit behind a protocol with two implementations (direct, Setapp).

### Gaps
- Paddle's own "which countries are supported" help page was not read directly; Brazil seller support rests on a third-party tracker that cites it. Paddle's verification requirements for Brazilian individuals/MEI were not found.
- FastSpring: no published rates and no official statement found on onboarding Brazil-based sellers or payout methods to Brazil.
- Dodo and Creem payout mechanics to Brazil (currency, rails, fees) were not verified beyond "Brazil listed".
- Brazilian tax treatment of foreign MoR payouts (service export, ISS/PIS/COFINS, FX/IOF on inbound transfers) was not researched; needs an accountant.
- Whether Polar, Lemon Squeezy, Gumroad, Dodo or Creem show Pix to Brazilian buyers was not established.
- No official Paddle statement was retrieved confirming Paddle Classic is closed to new signups or the status of the v4 Mac SDK; the claim comes from two third parties (one a competitor).
- Keygen's current pricing page was not read; no indie developer Setapp earnings reports from 2025-2026 were found.

## 6. Crash reporting and privacy-respecting analytics (Sentry, TelemetryDeck, MetricKit); what is acceptable for a privacy/security product

### Takeaway
The observed norm among 2026 Mac utilities is Sentry for crashes plus a no-PII event counter (TelemetryDeck or Aptabase), with consent, PII stripping and a published list of what is sent; practice splits on whether crash reports are opt-in or opt-out. For a security product, the strictest pattern found (crash data stays on disk unless the user opted in; keys absent from source builds) is the lowest-risk one.

### Cited Findings
- Sentry Cocoa on macOS: captures Mach exceptions, signals, C++/ObjC exceptions, `fatalError`/`precondition` messages, start-up crashes and app hangs; reports persist to disk and send on next launch; a manual step is needed to report uncaught exceptions on macOS; not available on macOS: session replay, feedback UI, screenshots, view hierarchy, watchdog terminations. SDK 9.25.0+ requires macOS 12. — [Sentry macOS features](https://docs.sentry.io/platforms/apple/guides/macos/features/)
- Sentry's MetricKit integration (macOS 12+) converts `MXHangDiagnostic`, `MXDiskWriteExceptionDiagnostic` and `MXCPUExceptionDiagnostic` into events; stack traces may contain only a few frames. — [Sentry MetricKit for macOS](https://docs.sentry.io/platforms/apple/guides/macos/configuration/metric-kit/)
- Sentry pricing (Oct 2026): Developer free, 1 user, 5K errors/month, 30-day lookback; Team $26/month billed annually ($29 monthly), 50K errors; Business $80/month. — [Sentry pricing](https://sentry.io/pricing/), [Devshot, 26 Oct 2026](https://devshot.co/blog/sentry-pricing)
- TelemetryDeck privacy model: stores a double-salted hashed installation ID, developer-defined event names, timestamp rounded to the hour, device/OS/app-version metadata; "Our servers never store IP addresses"; no lookup from your user IDs to theirs; aggregated OS/device data feeds a public survey that customers cannot opt out of; EU-hosted on Hetzner since April 2026 (per a third-party summary). — [TelemetryDeck FAQ](https://telemetrydeck.com/faq/), [techyorker comparison](https://techyorker.com/compare/aptabase-vs-telemetrydeck/)
- TelemetryDeck pricing change, 1 Jul 2026: free tier cut from 100,000 to 50,000 events/month for new accounts (existing accounts keep 100,000); first price increase since April 2023; ingestion stops when the free limit is hit. Paid plans from €9/month; free plan limited to 3 apps. — [TelemetryDeck pricing update, 1 Jul 2026](https://telemetrydeck.com/blog/pricing-update-2026/), [techyorker](https://techyorker.com/compare/aptabase-vs-telemetrydeck/)
- TelemetryDeck also categorises errors and crashes sent by the app. — [TelemetryDeck Swift page](https://telemetrydeck.com/platforms/swift/)
- Aptabase: open source (server AGPL-3.0, SDKs MIT), self-hostable with Docker, free up to 20,000 events/month, $10/month for 200,000; EU (Germany) or US region; cannot compute unique users/MAU by design. — [techyorker](https://techyorker.com/compare/aptabase-vs-telemetrydeck/), [mobilestalk](https://mobilestalk.net/compare/aptabase-vs-telemetrydeck/)

**What comparable Mac utilities do**
- MacWrench (system-maintenance utility; runs shell commands, cleans files): opt-in TelemetryDeck; own crash reporter hooks signals and `NSException`s, writes to disk, and sends (signal type, stack trace, app version) only if the user opted in, otherwise "the crash data sits on disk and never leaves your machine". — [MacWrench 1.1.7 release notes, 22 Feb 2026](https://macwrench.app/blog/release-1-1-7)
- Burrow (Mac system monitor): PostHog + Sentry, on by default with opt-out; random per-SDK install IDs not derived from hardware; counts bucketed into ranges; paths scrubbed (`/Users/<name>`); IP not stored (`sendDefaultPii = false`); full event list published in a TELEMETRY.md; SDK keys injected only at release so source builds send nothing. — [Burrow SECURITY.md](https://github.com/caezium/Burrow/blob/main/SECURITY.md)
- Osaurus (Mac AI app): usage analytics (Aptabase) strictly opt-in with events buffered until consent; crash reports (Sentry) on from first launch with opt-out, scoped to crashes and 3-second hangs only, tracing/profiling/network breadcrumbs off, hostname and user fields stripped. — [Osaurus telemetry docs](https://docs.osaurus.ai/telemetry)

### Inferences
- A defensible configuration for a security/privacy product: analytics opt-in at onboarding; crash reporting either opt-in or a clearly disclosed opt-out with a first-launch notice; Sentry with `sendDefaultPii = false`, path/hostname scrubbing in `beforeSend`, tracing and breadcrumbs off; a public TELEMETRY.md; no SDK keys in debug/source builds. Never include scan findings, file paths, process names or network destinations in events (bucket counts instead).
- The root helper should not link any telemetry SDK or make network calls; it should hand sanitized diagnostics to the app over XPC so that one unprivileged, user-controllable process is the only thing that phones home.
- Free tiers suffice at launch: Sentry Developer (5K errors, 1 user) and TelemetryDeck (50K events) or Aptabase (20K events).

### Gaps
- Whether MetricKit delivers crash diagnostics (`MXCrashDiagnostic`) on macOS for non-App-Store apps was not confirmed; the Sentry docs only list hang, disk-write and CPU diagnostics.
- Practices of the named reference vendors (Objective-See, Objective Development/Little Snitch, Rogue Amoeba, Proton, MacPaw) were not found; the three examples above are smaller apps.
- LGPD/GDPR consent analysis for crash reports was not researched.
- Self-hosted Sentry-compatible backends (GlitchTip, Bugsink) were not researched.

## 7. Build/CI: GitHub Actions macOS runners vs Xcode Cloud; reproducible builds; code-signing secrets

### Takeaway
GitHub-hosted macOS runners cost $0.062/minute ($3.72/hour) against Xcode Cloud's 25 included hours and ~$0.40-0.50/hour beyond, so Xcode Cloud is about 8x cheaper per hour; GitHub Actions wins on flexibility for a Developer ID + Sparkle pipeline that is just shell scripts. Secrets handling has a settled pattern: base64 `.p12` into a temporary keychain, App Store Connect API key for notarytool, Sparkle key on stdin.

### Cited Findings
- GitHub Actions per-minute rates: macOS 3-4 core (M1 or Intel) $0.062; macOS 12-core $0.077; Linux 2-core $0.006; every job rounded up to a whole minute. — [GitHub Docs: Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)
- Standard runner hardware: arm64 = 3 CPU (M1), 7 GB RAM; xlarge = 5-core M2, 14 GB at $0.102/min (Team/Enterprise orgs only). Included compute: Free $12/month (~193 macOS minutes), Pro $18 (~290). Standard runners are free for public repositories. Failed runs bill. — [macbox, 9 Nov 2026 (runner vendor)](https://macbox.build/guides/github-macos-runner-cost/)
- `macos-26` runner image GA since 26 Feb 2026 (arm64; `macos-26-intel` also available); image dated 2 Nov 2026 ships Xcode 26.0.1-26.6 with 26.6 default, Xcode 27 in public preview; macOS 14 arm64 runners retired 2 Nov 2026. — [GitHub changelog, 26 Feb 2026](https://github.blog/changelog/2026-02-26-macos-26-is-now-generally-available-for-github-hosted-runners/), [actions/runner-images macOS 26 readme](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md)
- Xcode Cloud (Apple prices read 5 Nov 2026): 25 compute hours/month included with the $99/year Apple Developer Program; 100 h $49.99/month; 250 h $99.99; 1,000 h $399.99; 10,000 h $3,999.99. Apple's unit: "running 5 tests of 12 minutes each equals one compute hour". — [macrun.dev (runner vendor)](https://macrun.dev/guides/xcode-cloud-alternative), [macbox](https://macbox.build/guides/github-macos-runner-cost/)
- Third-party macOS runners: $0.04-0.20/minute (Namespace, WarpBuild, Depot, Blacksmith — the last with 3,000 free minutes/month per runner type); dedicated Mac minis from $109-149/month (MacStadium), $139 (MacRun); a self-hosted Mac incurs no GitHub runner charge per one source. — [macswarm comparison, checked 25-27 Oct 2026 (vendor)](https://macswarm.com/compare/macos-ci-runners-pricing/), [macbox](https://macbox.build/guides/github-macos-runner-cost/)
- Code-signing secrets pattern used across current workflows: base64 `.p12` secret → `security create-keychain` with a random password in `$RUNNER_TEMP` → `set-keychain-settings -lut 21600` → `unlock-keychain` → `security import ... -T /usr/bin/codesign` → `set-key-partition-list -S apple-tool:,apple:,codesign:` → prepend to the keychain search list; delete the `.p12` afterwards. — [onelake-explorer-macos release.yml](https://github.com/sdebruyn/onelake-explorer-macos/blob/17b828032dd75f681f77231cf435debfc7ef012e/.github/workflows/release.yml), [lurar release.yml](https://github.com/lsjoberg/lurar/blob/main/.github/workflows/release.yml), [burn release-macos.yml](https://github.com/AgentWorkforce/burn/blob/main/.github/workflows/release-macos.yml)
- Typical secret set: Developer ID `.p12` + password, App Store Connect API key (`.p8` base64, key ID, issuer), Sparkle EdDSA private key; advice to pin the Xcode version in the workflow so a runner default change cannot silently break the build. — [Amore help](https://amore.computer/help/github-actions/)
- Same release lane can run locally (credentials in the login keychain / `notarytool` keychain profile) and in CI (env vars). — [Keyty Fastfile](https://github.com/keytyapp/Keyty/blob/9447819b/fastlane/Fastfile), [Quoin distribution docs](https://github.com/2389-research/Quoin/blob/main/docs/reference/distribution.md)
- Xcode 26 added compilation caching (faster clean builds and branch switches). — [Xcode 26 Release Notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes.md)

### Inferences
- Cheapest robust setup for a solo founder: run package tests on Linux/macOS runners with `swift test` where possible, keep macOS minutes for the signed build; a 15-minute signed+notarized release costs ~$0.93 on GitHub's standard runner, so releases are cheap and PR builds are the cost driver. Free included compute covers only ~3 hours of macOS per month on a private repo.
- Because signing a root helper with a Developer ID is the product's trust anchor, the lowest-exposure option is to sign and notarize on the founder's own Mac (or a self-hosted runner) with the same script, using hosted CI only for unsigned build+test; if hosted CI signs, restrict the release workflow to protected tags/environments with required approval.
- Xcode Cloud is priced attractively but oriented to App Store/TestFlight delivery; a Sparkle appcast + DMG pipeline needs custom `ci_scripts`, which is less documented than the GitHub Actions pattern.

### Gaps
- Apple's Xcode Cloud pricing page and GitHub's January 2026 pricing-change announcement were not read directly (figures come from GitHub Docs for Actions and from runner-vendor pages quoting Apple).
- No usable source on reproducible/deterministic builds for Swift/Xcode apps was found (e.g. bit-for-bit reproducibility with code signing, timestamps, or Swift Build determinism). Treat reproducible builds as an open question.
- Xcode Cloud support for Developer ID notarized export and custom post-build scripts for Sparkle was not verified.
- Hardware-backed or cloud-HSM storage of Developer ID keys for CI was not researched.
