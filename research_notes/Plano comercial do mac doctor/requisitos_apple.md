# Apple requirements for distributing a privileged macOS security/diagnostics app outside the Mac App Store (state as of 12 Nov 2026)

Version context used throughout: macOS 15 Sequoia (2024), macOS 26 Tahoe (released 15 Sep 2025), macOS 27 Golden Gate (released 14 Sep 2026, Apple silicon only; 27.0.1 on 28 Sep 2026, 27.2 in beta). "Verified" means I read the primary page in this session; "secondary" means a third party quoting Apple or reporting its own tests.

---

## 1. Developer ID signing, notarization, hardened runtime, stapling, Gatekeeper, cost, CI

### Takeaway
Direct distribution requires an Apple Developer Program membership, a Developer ID Application certificate (now from the G2 sub-CA, renewed annually), hardened runtime, a secure timestamp, notarization with `notarytool` and stapling. Since macOS 15 an un-notarized build is effectively unusable for ordinary users (no Control-click override), and two late-2026 deadlines matter: old-sub-CA `.pkg` installers stop installing on 1 Feb 2027, and macOS 27 is the last release with general Rosetta, so ship arm64/universal.

### Cited Findings
- Notarization is mandatory for Developer ID software: "Beginning in macOS 10.15, all software built after June 1, 2019, and distributed with Developer ID must be notarized." It is "an automated system", "not App Review". — [Apple: Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution.md)
- Exact notary prerequisites: every executable code-signed and valid; signed with a Developer ID application/kext/system-extension/installer certificate (not Mac Distribution, ad hoc, Apple Development); hardened runtime enabled on app and command-line targets; secure timestamp; no `com.apple.security.get-task-allow` = true; linked against macOS 10.9 SDK or later; properly formatted XML, ASCII-encoded entitlements. — [Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution.md)
- `altool` and Xcode 13 or earlier have been refused by the notary service since 1 Nov 2023; use `notarytool` (Xcode 14+) or the Notary REST API. `notarytool` and `stapler` ship with Xcode; accepted containers are ZIP, PKG and DMG. — [Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution.md); [Apple: Developer ID](https://developer.apple.com/developer-id/)
- Service-level statement (WWDC21): Apple "committed to completing this process within 15 minutes for 98 percent of Notary submissions, and most complete in under five"; `notarytool submit --wait` and webhook notifications exist for CI. Apple's doc says the scan "usually takes less than an hour". — [WWDC21 Faster and simpler notarization](https://www.youtube.com/watch?v=jRi49_uY73Y&vl=en); [Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution.md)
- Common rejection messages: "The binary is not signed with a valid Developer ID certificate." (wrong cert type; installers need Developer ID Installer); "The executable does not have the hardened runtime enabled." (fix: `--options=runtime`); stapler error -68 / -73 on old tools or read-only disk images. — [Apple: Resolving common notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues.md)
- Hardened runtime and plug-ins: plug-ins inherit the host's entitlements, so a host must carry every entitlement its plug-ins need. — [Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution.md)
- macOS 15 Sequoia: "users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security". — [Apple Developer News, 6 Aug 2024](https://developer.apple.com/news/?id=saqachfa)
- Gatekeeper checks on first open of quarantined software (Sequoia description from the Platform Security Guide, as summarised by Howard Oakley): identified developer signature, notarization ticket, CDHash (not altered), first-run XProtect scan. On macOS 26.0 a notarized quarantined app no longer gets the reported XProtect scan on first run, yet first launch still took about 10.4 s versus about 0.65 s on later runs; notarization is checked online via CloudKit on first run. — [Eclectic Light, 30 Sep 2025](https://eclecticlight.co/2025/09/30/do-apps-launch-faster-in-macos-tahoe/)
- macOS 27: `spctl` gains a purge command for Gatekeeper database entries of unmounted apps (radar 123097648). — [Apple: macOS 27 Golden Gate Release Notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes) (verified)
- Certificate authority change (Apple, 1 Oct 2026): "The original Developer ID Certification Authority (Sub-CA) expires on February 1, 2027. Certificates issued by this authority will stop working on that date." `.pkg` files signed with an affected certificate "will no longer install"; "Previously signed and notarized Mac software (with a secure timestamp) will keep working". The G2 sub-CA is valid until 2031 but certificates it issues "expire annually and must be renewed each year". — [Apple Developer News, 1 Oct 2026](https://developer.apple.com/news/?id=w4atic4c); [Apple: Replacing Developer ID certificates](https://developer.apple.com/help/account/certificates/replace-developer-id-certificates)
- Only the Account Holder can create Developer ID certificates; a team may hold up to five Developer ID Application and five Developer ID Installer certificates. — [Apple: Replacing Developer ID certificates](https://developer.apple.com/help/account/certificates/replace-developer-id-certificates)
- Certificate/profile lifetime rules: an app signed while the certificate was valid keeps running after the certificate expires; an app that uses a Developer ID provisioning profile (needed for restricted entitlements) stops launching when that profile expires (profiles created after 22 Feb 2017 last 18 years); a `.pkg` only installs while its Developer ID Installer certificate is valid. — [Apple: Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)
- Architecture: Apple (1 Sep 2026) calls macOS 27 the "Final release to support Rosetta"; macOS 26.4+ notifies users launching Rosetta apps. macOS 27 release notes: "All Intel-based software will no longer be compatible with macOS 28.0, excluding legacy games", and installer packages with no `hostArchitecture` now default to arm64 (radar 171187112). macOS 27 runs only on Apple silicon. — [Apple Developer News, 1 Sep 2026](https://developer.apple.com/news/?id=w5ngl9k2); [Apple: macOS 27 Release Notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes) (verified); [Apple Support: WWDC26 app management updates](https://support.apple.com/en-gb/guide/deployment/depd567c9ffa/web)
- Cost: Apple Developer Program is 99 USD per membership year and includes 25 Xcode Cloud compute hours per month; extra Xcode Cloud tiers are 100 h for US$49.99, 250 h for US$99.99, 1,000 h for US$399.99, 10,000 h for US$3,999.99 per month. — [Apple: Xcode Cloud get started](https://developer.apple.com/xcode-cloud/get-started/) (tiers verified); fee figure from [macbox guide, Nov 2026](https://macbox.build/guides/github-macos-runner-cost/) (secondary; Ars Technica 2024 also says "$100-a-year": [Ars](https://arstechnica.com/gadgets/2024/08/macos-15-sequoia-makes-you-jump-through-more-hoops-to-disable-gatekeeper-app-checks/))
- GitHub Actions: standard macOS runner (3- or 4-core) bills US$0.062 per minute, rounded up per job; larger macOS runners are US$0.077 (12-core Intel) and US$0.102 (M2 Pro). — [GitHub Docs: Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing) (verified); labels `macos-15`, `macos-26`, `xcode-27` reported by [macbox, Nov 2026](https://macbox.build/guides/github-macos-runner-cost/) (secondary)
- GitHub's documented signing pattern: base64 `.p12` and password in secrets, temporary keychain via `security create-keychain` / `import` / `set-key-partition-list`, delete afterwards. — [GitHub Docs: Installing an Apple certificate on macOS runners](https://docs.github.com/en/actions/how-tos/deploy/deploy-to-third-party-platforms/sign-xcode-applications)
- Notarization in CI is normally authenticated with an App Store Connect API key (`--key`, `--key-id`, `--issuer`; omit `--issuer` for individual keys), then `stapler staple`; `Apple-Actions/notarize` wraps submit/wait/log/staple and an `spctl` check for `source=Notarized Developer ID`. — [Apple-Actions/notarize](https://github.com/Apple-Actions/notarize); [Amore docs](https://amore.computer/help/github-actions/)
- A locally built, Developer ID-signed but un-notarized bundle runs on the build machine; `spctl --assess` reports `source=Unnotarized Developer ID` (macOS 26.6 measurement). — [MaestroRun TCC-FINDINGS](https://github.com/RunMaestro/MaestroRun/blob/main/docs/TCC-FINDINGS.md) (secondary, single project)
- Restricted entitlements under Developer ID need an embedded provisioning profile; one report shows a notarized app with `keychain-access-groups` failing on macOS 26.3 beta with AMFI "No matching profile found". — [RepoBar issue #29](https://github.com/steipete/RepoBar/issues/29) (anecdote, beta OS)

### Inferences
- Prefer shipping a notarized, stapled DMG or ZIP of a single `.app` (helper embedded) over a `.pkg`: apps signed with a secure timestamp survive certificate expiry, whereas packages are bound to installer-certificate validity and the 1 Feb 2027 cutoff.
- Because G2 certificates are annual, the release pipeline needs a yearly certificate rotation step and must sign by SHA-1 identity hash to avoid ambiguity when two same-named certs coexist.
- A solo developer's CI cost is small either way: a 10-minute signed/notarized release job is about US$0.62 on GitHub-hosted macOS, or free inside Xcode Cloud's 25 hours.

### Gaps
- I did not load Apple's enrollment page itself, so the 99 USD fee and any fee-waiver rules rest on secondary sources.
- Whether Xcode Cloud can perform Developer ID export plus notarization as a built-in post-action was not verified; assume `notarytool` in a custom script or GitHub Actions.
- No Apple source found for current notary turnaround in 2026 (the 15-minute figure is from 2021; one 2026 workflow comment budgets 30 to 90 minutes: [acuity workflow](https://github.com/paulhkang94/acuity/blob/main/.github/workflows/release.yml)).
- The macOS 27 release-note line "Fixed: `launchd` no longer supports loading `launchd` property list files with the quarantine extended attribute" (radar 166415497) is ambiguous as to shipped behaviour; one analyst flags both readings and had not tested it. — [Apple release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes); [Blake Crosley](https://blakecrosley.com/blog/macos-27-golden-gate-release)

## 2. Privileged helper architecture: SMAppService, deprecated APIs, XPC hardening

### Takeaway
The supported design on macOS 13+ is an unprivileged app plus a root LaunchDaemon embedded in the app bundle and registered with `SMAppService.daemon(plistName:)`, approved by an admin in Login Items, talking over a Mach-service XPC connection whose peer is pinned with a code-signing requirement. `SMJobBless` (deprecated macOS 13) and `AuthorizationExecuteWithPrivileges` (deprecated 10.7) should not be used for new code.

### Cited Findings
- `SMAppService.register()`: "If the service corresponds to a LaunchDaemon, the system won't bootstrap the LaunchDaemon until an admin approves the LaunchDaemon in System Preferences"; returns `kSMErrorLaunchDeniedByUser` when not approved and `kSMErrorAlreadyRegistered` when already registered. Agents bootstrap immediately and must be registered once per user. — [Apple: SMAppService.register()](https://developer.apple.com/documentation/servicemanagement/smappservice/register().md)
- Bundle layout: daemon plist in `Contents/Library/LaunchDaemons`, agent plist in `Contents/Library/LaunchAgents`, use `BundleProgram` (bundle-relative) instead of `Program`. Register daemons first: "If the user authorizes the LaunchDaemon, the system approves all the other helper executables present in the app bundle". Check `status` at launch and call `SMAppService.openSystemSettingsLoginItems()` when approval is missing. Legacy plists should add `AssociatedBundleIdentifiers`; `statusForLegacyPlist(at:)` reports their state. — [Apple: Updating helper executables from earlier versions of macOS](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos.md)
- Quinn's worked example (Sept 2025): first `register()` of a daemon fails with `SMAppServiceErrorDomain / 1` and shows the notification "Background Items Added ... added items that can run in the background for all users. Do you want to allow this?"; the answer is remembered and reset with `sfltool resetbtm`. A sandboxed app can no longer install a non-sandboxed daemon since macOS 14.2. A job with restricted entitlements needs an app-like wrapper to hold the provisioning profile. — [Apple Developer Forums, Service Management tag](https://developer.apple.com/forums/tags/servicemanagement?page=3)
- Status values: `.notRegistered`, `.enabled`, `.requiresApproval`, `.notFound`. With SMAppService the plist and executable stay inside the app bundle and are not copied to `/Library/LaunchDaemons` or `/Library/PrivilegedHelperTools`. — [Csaba Fitzl, SMAppService quick notes](https://theevilbit.github.io/posts/smappservice/)
- `SMJobBless` header: `__OSX_DEPRECATED(10.6, 13.0, "Please use SMAppService instead")`; `AuthorizationExecuteWithPrivileges` is marked deprecated in the 10.7 SDK but not removed. The `SMAppService.h` header (macOS 27 SDK) is reported to state that apps containing daemons must be notarized, that a changed plist or executable must be re-registered, and that the app should live in `/Applications` for boot-time start. `unregister` kills the running job. — [Daniel Cosenza, Oct 2026](https://danielcosenza.com/posts/mac-smjobbless-privileged-helper-lifecycle/) (secondary, quoting local SDK headers)
- Managed Macs: a Service Management managed-login-items payload auto-approves items matching `BundleIdentifier`, `BundleIdentifierPrefix`, `TeamIdentifier`, `Label` or `LabelPrefix` rules. — [Apple Support: Manage login items and background tasks on Mac](https://support.apple.com/guide/deployment/manage-login-items-background-tasks-mac-depdca572563/web)
- macOS 26 Tahoe UI change (press report): a new popup appears when an app tries to run a background process after being closed, with "Always Allow" or deny. — [MacRumors, 24 Sep 2025](https://www.macrumors.com/2025/09/24/all-the-new-macos-tahoe-features/) (secondary)
- XPC vulnerability class 1, PID-based client checks: a client can queue a message and then replace its image with a trusted binary using `posix_spawn` with `POSIX_SPAWN_SETEXEC | POSIX_SPAWN_START_SUSPENDED`, keeping the PID. Real cases: F-Secure (CVE-2020-14977) and Malwarebytes. Fix: validate with the audit token. — [Csaba Fitzl, Secure coding XPC part 5](https://theevilbit.github.io/posts/secure_coding_xpc_part5/); [Wojciech Reguła, Say no to the PID](https://wojciechregula.blog/post/learn-xpc-exploitation-part-2-say-no-to-the-pid/)
- Class 2, connection-level audit token race: `xpc_connection_get_audit_token` can return the wrong token when called outside an event handler or when a reply races a message; Apple fixed `smd` by switching to `xpc_dictionary_get_audit_token`. Hardening advice: check authorization before accepting the connection, drop the connection on unrecognised messages, and use the built-in APIs `-[NSXPCConnection setCodeSigningRequirement:]` (macOS 13.0+) or `xpc_connection_set_peer_code_signing_requirement` (macOS 12.0+). — [Thijs Alkemade, OBTS v6 slides](https://objectivebythesea.org/v6/talks/OBTS_v6_tAlkemade.pdf)
- Class 3, weak requirement: checks often cover only `anchor apple generic` plus Team ID; bundle ID, minimum client version, absence of dangerous entitlements and hardened-runtime/library-validation flags are rarely checked, so an attacker can inject into an old or unhardened client of the same vendor and talk to the helper. Recommended requirement adds an identifier and a version-style entitlement. — [XPC Client Validation slides (IT-SECX)](https://itsecx.ustp.at/content/download/413776/file/5_XPC%20Client%20Validation%20Music%20to%20my%20ears!.pdf); [Csaba Fitzl, Secure coding XPC part 2](https://theevilbit.github.io/posts/secure_coding_xpc_part2/)
- Hardened runtime is itself a security control for the client: an ad hoc build without it honoured `DYLD_INSERT_LIBRARIES`; with `--options runtime` dyld ignored it (macOS 26.6). — [MaestroRun TCC-FINDINGS](https://github.com/RunMaestro/MaestroRun/blob/main/docs/TCC-FINDINGS.md) (secondary)
- Usage rule for `setCodeSigningRequirement:`: set once before `resume`; a malformed string raises an exception; a non-conforming peer invalidates the connection. A newer low-level listener API, `xpc_listener_set_peer_requirement` with `xpc_peer_requirement_t`, is described as macOS 26+; sessions created from the listener do not inherit it. Audit-token-then-PID fallback patterns re-open the race (seen in a 2026 analysis of Intego). — [HackTricks: macOS PID reuse](https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-proces-abuse/macos-ipc-inter-process-communication/macos-xpc/macos-xpc-connecting-process-check/macos-pid-reuse.html) (secondary)
- `SecCodeCreateWithXPCMessage` (macOS 11+) validates the sender of a specific message using its audit token. — [securing/SimpleXPCApp issue #1](https://github.com/securing/SimpleXPCApp/issues/1) (secondary)
- Apple's secure coding guidance: least privilege, factor privileged work into a separate helper, and "Elevating privileges is not allowed in applications submitted to the Mac App Store". — [Apple: Elevating Privileges Safely (archive)](https://developer.apple.com/library/archive/documentation/Security/Conceptual/SecureCodingGuide/Articles/AccessControl.html)

### Inferences
- For the stated feature set (bootout/disable launchd items, kill other users' or root processes, move root-owned files to a quarantine folder), a single on-demand root daemon (no `KeepAlive`, launched by Mach-service lookup) with a narrow, typed XPC protocol is the least-privilege shape; the GUI should never run as root.
- The helper should expose verbs with validated arguments (for example "bootout label X in domain Y", "quarantine path P") rather than "run command", and should re-validate paths server-side to avoid symlink/TOCTOU abuse, since the vulnerability literature shows the helper's API surface is the real attack target once client validation is correct.
- A suitable requirement string is `anchor apple generic and identifier "<bundle id>" and certificate leaf[subject.OU] = "<TEAMID>"` plus a minimum-version condition, applied with `setCodeSigningRequirement:` (deployment target macOS 13+).
- User experience cost: one admin approval in System Settings > General > Login Items & Extensions; the app must detect `.requiresApproval` and deep-link there.

### Gaps
- I could not open Apple's own `SMAppService` class page or the SDK header in this session; the notarization requirement for daemon-bearing apps is from a secondary source quoting the header.
- The macOS 26 `XPCPeerRequirement` / `xpc_listener_set_peer_requirement` API was not confirmed against Apple documentation.
- No authoritative list of SMAppService bugs specific to macOS 26/27 was found; older reports note agents stuck in "requires approval" after daemon approval ([Outset 4.0 beta notes](https://github.com/macadmins/outset/releases/tag/v4.0-Beta-2)).

## 3. Full Disk Access and TCC

### Takeaway
Full Disk Access (FDA, service `SystemPolicyAllFiles`) can only be granted by the user in System Settings or by an MDM PPPC profile; there is no API to request or query it. Two late-2026 developments directly threaten a "read TCC.db" feature: macOS 27's release notes deprecate direct app access to the local TCC database, and Apple announced on 2 Oct 2026 that FDA will get additional, more explicit user controls.

### Cited Findings
- macOS 27 release notes, section TCC, Deprecations: "Apps can no longer access the local TCC database directly." (radar 90775556). — [Apple: macOS 27 Golden Gate Release Notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes) (verified verbatim)
- Apple's enterprise notes are reported to add a `tccutil list` command that "can report current privacy authorizations for specified services or apps on managed devices"; on an unmanaged Mac running 27.0 the binary carries the verb but only prints the `reset` usage line. — [Blake Crosley, macOS 27 GA post](https://blakecrosley.com/blog/macos-27-golden-gate-release) (secondary)
- Conflicting observation: the same author reports that on macOS 27.0 (build 26A428) a single-row read of the system TCC database from a shell whose terminal held FDA still returned a row, while the same read as a launchd job without an FDA-holding responsible process got "authorization denied". — [Blake Crosley, Full Disk Access and AI agents](https://blakecrosley.com/blog/macos-full-disk-access-ai-agents) (secondary, one machine)
- Apple, 2 Oct 2026: "Full Disk Access largely sidesteps these controls in order to allow backup apps to function properly on the Mac... Going forward, we will introduce additional controls to ensure that users who genuinely wish to grant an app this extraordinary level of access can only do so with very explicit user action." No version, date or API given. — [Apple Developer News, 2 Oct 2026](https://developer.apple.com/news/?id=p6zjojqw); context in [TidBITS](https://tidbits.com/2026/10/05/apple-plans-to-tighten-full-disk-access-controls/) and [Daring Fireball](https://daringfireball.net/2026/10/apple_full_disk_access)
- "TCC has no API surface." FDA is system wide, Files and Folders is per user. MAC privileges hinge on "responsible code"; if a launchd daemon or agent is not attributed to the app, add `AssociatedBundleIdentifiers`. Managed sites use the `com.apple.TCC.configuration-profile-policy` payload. — [Quinn, On File System Permissions (Apple Developer Forums)](https://developer.apple.com/forums/thread/678819)
- Quinn (June 2024, as quoted): for a launchd job, "If the daemon or agent was installed by SMAppService, that makes the app the responsible code. Otherwise, the daemon or agent should include AssociatedBundleIdentifiers"; the algorithm "is not documented, has changed in the past, and may well change in the future." — [Blake Crosley quoting the forum thread](https://blakecrosley.com/blog/macos-full-disk-access-ai-agents) (secondary quote of Apple staff post)
- History shows this is fragile: macOS 11.4 stopped helper tools launched via launchd from inheriting the main app's FDA, while `NSTask` children kept inheriting; Carbon Copy Cloner had to tell users to add its helper, not the app, to FDA. — [Michael Tsai, June 2021](https://mjtsai.com/blog/2021/06/01/macos-11-4-breaks-full-disk-access-for-helper-tools/); [Eclectic Light, 2018](https://eclecticlight.co/2018/09/13/helper-tools-mojaves-privacy-and-high-sierra-intricate-relationships/)
- Measurements on macOS 26.6: TCC judges the responsible process; children via `execve`/`posix_spawn` inherit every grant (and every denial) the identity holds; a process started directly by launchd with no granted identity gets nothing; a grant survives rebuilds signed with the same identifier and team. — [MaestroRun TCC-FINDINGS](https://github.com/RunMaestro/MaestroRun/blob/main/docs/TCC-FINDINGS.md) (secondary)
- Vendor practice for MDM: separate PPPC entries are created for the app (bundle ID) and for the privileged helper (path identifier with its own code requirement), both for `SystemPolicyAllFiles`. — [Root3 App Catalog docs](https://docs.appcatalog.cloud/articles/1402094-full-disk-access-pppc)
- Database locations: system `/Library/Application Support/com.apple.TCC/TCC.db` (holds FDA), per user `~/Library/Application Support/com.apple.TCC/TCC.db`, MDM decisions in `MDMOverrides.plist`; SIP-protected, not writable even by root, readable only with FDA; schema undocumented and has changed between releases. PPPC can allow FDA, Accessibility, Automation and Files and Folders, can only deny Camera and Microphone, and is honoured only via user-approved or automated MDM enrollment. — [Mac Hardening, Sep 2026](https://www.machardening.com/en/blog/tcc-privacy-permissions) (secondary)
- macOS 27 management changes: Accessibility grants via `com.apple.TCC.configuration-profile-policy` were deprecated in 26.2 and removed in 27; a new `Privacy` key in `com.apple.configuration.app.settings` sets default permissions with one consolidated consent prompt; the corresponding TCC-profile keys are deprecated in macOS 27. — [Apple Support: WWDC26 app management updates](https://support.apple.com/en-gb/guide/deployment/depd567c9ffa/web)
- User flow facts: apps cannot ask for FDA; attempting to open a protected file makes the app appear (unchecked) in the FDA list, and the app can open the pane for the user. WWDC19 stated apps "can guide the user to the security and privacy preference pane". — [TidBITS discussion, Oct 2026](https://tidbits.com/2026/10/05/apple-plans-to-tighten-full-disk-access-controls/); WWDC19 701 as summarised in [Blake Crosley](https://blakecrosley.com/blog/macos-full-disk-access-ai-agents) (secondary)
- Revoking permissions: `tccutil reset SERVICE [BUNDLE_ID]` is the only supported modification verb. — [Blake Crosley GA post](https://blakecrosley.com/blog/macos-27-golden-gate-release) (secondary); no add API per [Quinn](https://developer.apple.com/forums/thread/678819)
- macOS 27 SIP changes: access to other teams' app data containers and app group containers "no longer prompts the user for authorization; such accesses are denied by default" (radar 161835690); "XProtect may now restrict access to app data that is commonly targeted by malicious software" (radar 178668601); known issue: a process without a bundle ID cannot be granted per-container access, workaround is FDA. — [Apple: macOS 27 Release Notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes) (verified)
- Other data needing FDA: the BTM store under `/private/var/db/com.apple.backgroundtaskmanagement/` (see section 6). — [objective-see/DumpBTM](https://github.com/objective-see/DumpBTM)
- Local network privacy (macOS 15+): does not apply to code running as root (launchd daemons) but does prompt for launchd agents. — [Michael Tsai quoting Quinn, Oct 2024](https://mjtsai.com/blog/2024/10/02/local-network-privacy-on-sequoia/)

### Inferences
- Treat TCC.db parsing as a best-effort, version-gated feature: fine on macOS 15 and 26 with FDA, at risk on 27 and later. Plan a fallback (for example parsing `tccutil list` output where it works, or dropping the feature to "open the Privacy pane").
- Grant target: with an SMAppService-embedded daemon the app should be the responsible code, so one FDA toggle for the app should cover the daemon, but given the 11.4 regression and Quinn's caveat the app must test this per OS release and be ready to instruct users to add the helper separately. A single bundle identity for both keeps the user-facing list to one row.
- Reading launchd plists in `/Library/LaunchDaemons`, `/Library/LaunchAgents` and `~/Library/LaunchAgents`, process lists and the app's own data does not require FDA (these are not among the MAC-protected locations cited), so the app can offer a useful "no FDA" tier and ask for FDA only for BTM, TCC and other-app containers.
- Revoking another app's TCC permission means running `/usr/bin/tccutil reset` (per service, per bundle ID); there is no per-entry "set to deny" API, so the UI should say "reset" and not "revoke".
- Onboarding should (1) touch a protected path so the app pre-populates in the FDA list, (2) open `x-apple.systempreferences:` deep link to the pane, (3) poll by retrying the protected read, (4) handle the "quit and reopen" requirement.

### Gaps
- Apple has not said how the "local TCC database" restriction is enforced in macOS 27 or whether FDA still permits reads long term; the one field report says reads still worked on 27.0.
- No detail yet on the announced FDA "additional controls" (timing, whether security tools get an entitlement or exemption).
- I found no Apple documentation of a supported way to detect FDA; probing a protected file is community practice only.
- The exact deep-link URL string for the FDA pane on macOS 26/27 was not verified against a primary source.

## 4. Endpoint Security, System Extensions, Network Extension

### Takeaway
`com.apple.developer.endpoint-security.client` is a restricted entitlement that Apple grants case by case, mainly to registered companies building security products; it is needed for real-time monitoring/blocking, not for an on-demand scanner. Per-process network visibility for an on-demand view can come from libproc; live flow monitoring or blocking needs a Network Extension content filter (self-serve entitlement) packaged as a system extension.

### Cited Findings
- Entitlement definition: "The entitlement required to monitor system events for potentially malicious activity. You must request this entitlement from Apple"; without it `es_new_client` fails with `ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED`. — [Apple docs mirror: endpoint-security.client](https://apple-docs.everest.mt/docs/bundleresources/entitlements/com.apple.developer.endpoint-security.client/)
- System extensions cover network extensions and endpoint security clients in user space; "If you plan to ... use the EndpointSecurity API, you'll need to request an entitlement from Apple. While your request is in review, you can test system extensions on your Mac by temporarily turning off System Integrity Protection." — [Apple: System Extensions](https://developer.apple.com/system-extensions/)
- Runtime requirements (WWDC20): the ES entitlement; an extra entitlement on the containing app to install a system extension; user approval of the extension; FDA consent (pre-populated in the list when deployed as a system extension); MDM payloads can pre-approve the extension and FDA. — [WWDC20 Build an Endpoint Security app](https://developer.apple.com/videos/play/wwdc2020/10159/)
- An ES client must run as root with FDA and the entitlement. — [Objective-See, 27 Mar 2025](https://objective-see.org/blog/blog_0x7F.html)
- How to apply and how hard it is (Patrick Wardle): form at `developer.apple.com/contact/request/system-extension/`; Apple is "cautious about granting requests ... even to renowned security companies"; "register as a company"; "I'm aware of only one instance in which Apple granted the Endpoint Security client entitlement to an individual"; "be prepared to wait". After approval, enable Endpoint Security on the App ID and create a Developer ID provisioning profile. BlockBlock keeps ES logic in a launch daemon and not a system extension. — [The Art of Mac Malware vol. 2, ch. 11](https://taomm.org/vol2/pdfs/CH%2011%20Persistence%20Monitor.pdf)
- One developer's timeline: approval "took a little less than a month". — [prodisup.com, 2021](https://prodisup.com/posts/2022/01/building-and-testing-an-endpoint-security-macos-system-extension-on-bitrise/) (single anecdote)
- Useful ES events for this product class: `ES_EVENT_TYPE_NOTIFY_BTM_LAUNCH_ITEM_ADD` / `_REMOVE` (macOS 13.0; add event was buggy until 13.3), `ES_EVENT_TYPE_NOTIFY_GATEKEEPER_USER_OVERRIDE` (15.0), `ES_EVENT_TYPE_NOTIFY_TCC_MODIFY` (15.4; fires only when a permission is granted or revoked). — [Objective-See, Mar 2026](https://objective-see.org/blog/blog_0x86.html); [Objective-See, Mar 2025](https://objective-see.org/blog/blog_0x7F.html); [DEF CON 31 BTM slides](https://media.defcon.org/DEF%20CON%2031/DEF%20CON%2031%20presentations/Patrick%20Wardle%20-%20Demystifying%20%28%20Bypassing%29%20macOS%27s%20Background%20Task%20Management.pdf)
- macOS 26.3 and 26.4 SDKs add undocumented `ES_EVENT_TYPE_RESERVED_0` to `_6`; reverse engineering indicates `RESERVED_5`/`_6` are network-connection AUTH/NOTIFY events (15-second AUTH deadline). Wardle's caveats: undocumented, Apple "will likely object if you use this in production code", and Network Extensions "allow you to grant yourself the needed entitlement (e.g. content-filter-provider-systemextension)". — [Objective-See, 26 Mar 2026](https://objective-see.org/blog/blog_0x86.html)
- Network Extension content filter: `NEFilterDataProvider` receives TCP/UDP flows (read-only, allow/drop verdict); `NEFilterPacketProvider` gets packets on macOS; the provider runs in a system extension so it works with no user logged in; `NEFilterManager` in the app registers the configuration. — [WWDC19 Network Extensions for the Modern Mac](https://developer.apple.com/videos/play/wwdc2019/714/); [WWDC25 Filter and tunnel network traffic](https://developer.apple.com/videos/play/wwdc2025/234/)
- The new URL Filter capability (OS 26) must be applied for and requires an Oblivious HTTP relay validated by Apple before Developer ID distribution. — [WWDC25 session 234](https://developer.apple.com/videos/play/wwdc2025/234/)
- macOS 27 MDM: a `com.apple.configuration.app.settings` configuration "uses the Endpoint Security extension framework" to manage which binaries may run on supervised Macs. — [Apple Support: WWDC26 app management updates](https://support.apple.com/en-gb/guide/deployment/depd567c9ffa/web)
- `eslogger(1)` (ships with macOS) requires the responsible process to hold FDA. — [Blake Crosley citing the man page](https://blakecrosley.com/blog/macos-full-disk-access-ai-agents) (secondary)

### Inferences
- An on-demand scanner (KnockKnock-style enumerate, verify signatures, show connections) needs no ES entitlement and no system extension; version 1 can ship without waiting on Apple. Apply for the ES entitlement early as a company if real-time protection is on the roadmap, and budget weeks to months with a real chance of refusal for a small or individual developer.
- Real-time network monitoring means a second approval prompt (system extension plus "Allow filter" network prompt) and more support burden; keep it an optional module.
- Do not build on the reserved ES network events.

### Gaps
- Apple publishes no approval criteria or timelines for the ES entitlement; evidence is anecdotal (one "under a month" report from 2021, Wardle's qualitative account).
- I did not verify the current exact Network Extension entitlement values for Developer ID (`content-filter-provider-systemextension`) against Apple's entitlement page.
- No source confirmed whether macOS 27 changed system-extension approval UI.

## 5. Why not the Mac App Store, and what a "lite" edition could do

### Takeaway
Guideline 2.4.5 requires App Sandbox and forbids root escalation, shared-location installs and non-consensual background processes, which rules out the helper daemon, launchd management, killing arbitrary processes and reading TCC/BTM stores. A sandboxed lite edition is limited to what the user explicitly grants through the Open panel.

### Cited Findings
- Guideline 2.4.5: (i) "They must be appropriately sandboxed"; (ii) no third-party installers, self-contained bundle, "cannot install code or resources in shared locations"; (iii) no auto-launch or lingering processes without consent; (iv) may not download or install standalone apps, kexts or additional code; (v) "They may not request escalation to root privileges or use setuid attributes"; (vi) no license keys or own copy protection; (vii) updates only through the Mac App Store. — [Apple: App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Guideline 2.4.4: apps should not suggest disabling security features or modifying unrelated system settings. — [Apple: App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- Sandbox rules: every Mach-O in the bundle must be sandboxed; file-access exceptions must not be used to reach other apps' or the system's data; Apple-event exceptions for Finder/System Events "will likely result in rejection". — [Apple TN QA1773](https://developer.apple.com/library/archive/qa/qa1773/_index.html); [Apple QA1888](https://developer.apple.com/library/archive/qa/qa1888/_index.html)
- A sandboxed app cannot install a non-sandboxed daemon (blocked since macOS 14.2); a sandboxed app may register a sandboxed agent via SMAppService. — [Quinn, Apple Developer Forums](https://developer.apple.com/forums/tags/servicemanagement?page=3)
- What comparable sandboxed cleaners report: scan limited to home folder and user-chosen folders via `NSOpenPanel` plus security-scoped bookmarks; no APFS snapshot listing, no admin commands, no startup-item management, no CLI; `NSHomeDirectory()` resolves to the container; temporary-exception entitlements for home-relative paths are a review red line. — [MacZentra](https://maczentra.com/blog/mac-app-store-sandbox-what-changes); [DEV: What App Sandbox takes away from a Mac disk cleaner, Sep 2026](https://dev.to/ran_guo_5ed7f647ab1b09c50/what-app-sandbox-actually-takes-away-from-a-mac-disk-cleaner-5cmo) (both secondary vendor accounts)
- Mac App Store builds are not notarized by the developer; App Store submission covers the equivalent checks. — [Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution.md)

### Inferences
- A legal lite edition could offer: system health read-outs from public APIs (thermal state, battery, memory, disk space), a list of the user's own processes, static inspection of launch-agent folders the user grants via Open panel, code-signature checks on user-selected apps, and educational deep links to System Settings. It could not disable/bootout items, kill other processes, read TCC.db/BTM, or install the helper.
- The lite edition needs a separate bundle ID and licensing model (no license keys; StoreKit) and cannot upsell by downloading the full helper in-app (2.4.5 iv); linking to the website for the full edition is the common pattern but its review acceptance was not verified.

### Gaps
- No Apple statement on whether App Review accepts security/"antivirus" utilities that ask users for whole-disk folder grants; evidence is vendor experience only.
- Whether a sandboxed app can enumerate other users' or system processes with libproc was not verified.

## 6. Apple APIs to replace shelling out to command-line tools

### Takeaway
Process, socket, memory and code-signing data have usable C/Swift APIs (libproc, sysctl, Mach host statistics, Security framework). Launchd state, BTM and TCC have no public read API, so those remain file parsing or invoking Apple's own tools from the helper.

### Cited Findings
- BTM: no public API; "the BTM apis are in a private BackgroundTaskManagement.framework". `sfltool dumpbtm` needs root; the store is a serialized `NSKeyedArchiver` binary plist at `/private/var/db/com.apple.backgroundtaskmanagement/BackgroundItems-v*.btm` and reading it needs FDA. The version suffix changes across releases (v4 and v7 on macOS 13.x, v8, v9, v13, v16 seen later). — [osquery Slack, May 2024](https://chat.osquery.io/t/18785975/is-there-a-table-that-includes-macos-information-similar-to-); [objective-see/DumpBTM](https://github.com/objective-see/DumpBTM); [Crash Security BTM notes](https://blog.crashsecurity.io/macos-research/b/FC3F508F-3AF5-42BC-8573-E08B059A8E0E/Background-Task-Management-(BTM)); [Mac Forensics](https://www.macforensics.app/en/artifacts/login-items-btm)
- Open-source parsers: Objective-See `DumpBTM` (Objective-C library, used by KnockKnock's BTM plugin, which skips disabled items and distrusts Apple binaries persisted by non-system plists) and `BTMParser` (Swift package). BTM record fields include type flags (`0x2` app, `0x4` login item, `0x8` agent, `0x10` daemon, `0x10000` legacy), disposition flags (`0x1` enabled, `0x2` allowed, `0x4` hidden, `0x8` notified), team identifier, URL, executable path, associated bundle IDs. — [KnockKnock BTM.m](https://github.com/objective-see/KnockKnock/blob/main/Plugins/BTM.m); [hewigovens/BTMParser](https://github.com/hewigovens/BTMParser); [Mac Forensics](https://www.macforensics.app/en/artifacts/login-items-btm)
- Since SMAppService, persistence can live inside app bundles (`Contents/Library/LaunchAgents|LaunchDaemons`) and not only in the classic folders, so scanners must look there too. — [Csaba Fitzl](https://theevilbit.github.io/posts/smappservice/)
- Own-app service state: `SMAppService.status`, `statusForLegacyPlist(at:)`, `openSystemSettingsLoginItems()`. — [Apple: Updating helper executables](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos.md)
- Per-process sockets: `proc_listpids(PROC_ALL_PIDS)`, `proc_pidinfo(pid, PROC_PIDLISTFDS)`, then `proc_pidfdinfo(pid, fd, PROC_PIDFDSOCKETINFO)` yields family, protocol, local/remote address and port and TCP state (constants in `sys/proc_info.h`). — [The Art of Mac Malware vol. 2, ch. 4](https://taomm.org/vol2/pdfs/CH%204%20Network%20State%20and%20Statistics.pdf); working code in [OSHI MacInternetProtocolStatsJNA](https://www.oshi.ooo/xref/oshi/software/os/mac/MacInternetProtocolStatsJNA.html)
- Permission model for that approach: works for same-user processes; root needed for other users' processes. — [OSHI issue #3254](https://github.com/oshi/oshi/issues/3254) (secondary)
- System-wide flows with byte counters: `NetworkStatistics.framework` (what `nettop` uses) is private, with no public headers (`NStatManagerCreate`, `NStatManagerAddAllTCP/UDP`, `NStatManagerQueryAllSourcesDescriptions`); the underlying `com.apple.network.statistics` kernel-control socket is also private but usable unprivileged for the user's own flows. `nettop -L` gives CSV without root. — [TAOMM vol. 2 ch. 4](https://taomm.org/vol2/pdfs/CH%204%20Network%20State%20and%20Statistics.pdf); [netpeek README](https://github.com/lucasdaddiego/netpeek/blob/master/README.md); [SANS ISC](https://isc.sans.edu/diary/30160)
- Process and memory: `proc_pid_rusage` for per-process resource usage; `host_statistics64` with `HOST_VM_INFO64` for VM statistics; `sysctl` for `net.inet.*` stats. — [JNA SystemB reference](https://java-native-access.github.io/jna/5.19.1/javadoc/com/sun/jna/platform/mac/SystemB.html)
- Code-signing checks: `SecRequirementCreateWithString`, `SecCodeCopyGuestWithAttributes`, `SecCodeCheckValidityWithErrors` appear in helper validation code; `SecCodeCreateWithXPCMessage` since macOS 11. — [Csaba Fitzl part 2](https://theevilbit.github.io/posts/secure_coding_xpc_part2/); [SimpleXPCApp issue](https://github.com/securing/SimpleXPCApp/issues/1)
- Responsible-process lookup is exposed only via `launchctl procinfo <pid>` (root) or private `responsibility_*` symbols. — [Qt blog](https://www.qt.io/blog/the-curious-case-of-the-responsible-process); [MaestroRun TCC-FINDINGS](https://github.com/RunMaestro/MaestroRun/blob/main/docs/TCC-FINDINGS.md)
- macOS 27 adds Swift `stat`/`lstat`/`fstat` wrappers in the System library. — [Blake Crosley quoting release notes](https://blakecrosley.com/blog/macos-27-golden-gate-release) (secondary)
- macOS 27 unified-log archives cannot be read on macOS 26.1 or earlier (26.2+ required). — [Blake Crosley, release notes digest](https://blakecrosley.com/blog/macos-27-release-notes) (secondary)

### Inferences
- Practical mapping: `ps`/`lsof -i` to libproc; `vm_stat`/memory pressure to `host_statistics64` plus the dispatch memory-pressure source; `codesign -dv`/`spctl` to `SecStaticCode*`; launchd inventory to plist parsing of the classic folders plus app-bundle folders plus the BTM store; `launchctl bootout/disable/kill` and `tccutil reset` remain subprocess calls made by the root helper with fixed absolute paths and validated arguments.
- Because the BTM file format is private and its version number moves with OS releases, the parser needs a tolerant decoder, a per-OS test matrix and a fallback to `sfltool dumpbtm` run by the helper.
- Private NetworkStatistics use is a notarization-compatible but unsupported dependency; libproc snapshots are the safer default.

### Gaps
- I found no source in this session for: a public launchd enumeration API (believed absent; `SMJobCopyDictionary`/`SMCopyAllJobDictionaries` are long deprecated, unverified here), `ProcessInfo.thermalState`, IOKit power-source APIs (`IOPSCopyPowerSourcesInfo`), MetricKit applicability on macOS, `kern.memorystatus_vm_pressure_level`, or the quarantine-attribute APIs. These are from background knowledge and must be confirmed against Apple docs before the report relies on them.
- Whether the root helper needs FDA to read other processes' file descriptors, and whether libproc returns data for platform binaries under SIP, was not verified.

## 7. 2025-2026 macOS changes that affect security tools

### Takeaway
The direction is consistently toward less direct access: Gatekeeper overrides got harder (15), TCC and BTM events moved into Endpoint Security (13 to 15.4), and macOS 27 deprecates direct TCC database access, denies cross-team container reads by default, drops Intel, and precedes an announced FDA clampdown.

### Cited Findings
- macOS 15.0: Control-click Gatekeeper override removed. — [Apple Developer News](https://developer.apple.com/news/?id=saqachfa)
- macOS 15.0: new ES event `GATEKEEPER_USER_OVERRIDE`; 15.4: `TCC_MODIFY`. — [Objective-See](https://objective-see.org/blog/blog_0x86.html)
- macOS 15: app group container protection added to the MAC list (14 added app container protection, 13 app bundle protection). — [Quinn, On File System Permissions](https://developer.apple.com/forums/thread/678819)
- macOS 26.0 (15 Sep 2025): security content includes a Gatekeeper bypass fix in System Settings (CVE-2025-43296). — [Apple Support 125110](https://support.apple.com/en-us/125110)
- macOS 26.0: notarized apps skip the reported first-run XProtect scan; Tahoe also logs explicit decisions about scanning other processes. — [Eclectic Light](https://eclecticlight.co/2025/09/30/do-apps-launch-faster-in-macos-tahoe/)
- macOS 26.2: Accessibility via TCC profile deprecated; 26.3/26.4: reserved ES events; 26.4: Rosetta launch notifications. — [Apple Support deployment guide](https://support.apple.com/en-gb/guide/deployment/depd567c9ffa/web); [Objective-See](https://objective-see.org/blog/blog_0x86.html); [Apple Developer News, 1 Sep 2026](https://developer.apple.com/news/?id=w5ngl9k2)
- macOS 27.0 (verified release-note entries): TCC database direct access deprecated (90775556); cross-team container access denied by default (161835690); XProtect may restrict access to commonly targeted app data (178668601); `spctl` purge (123097648); launchd/quarantined plist entry (166415497); Rosetta deprecations. — [Apple: macOS 27 Release Notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)
- macOS 27 platform: Apple silicon only; App Attest available for Mac apps; ManagedApp framework on macOS; binary allow/deny management via ES for supervised Macs. — [Apple Support: WWDC26 app management updates](https://support.apple.com/en-gb/guide/deployment/depd567c9ffa/web)
- 1 Oct 2026: Developer ID sub-CA expiry notice (1 Feb 2027). 2 Oct 2026: FDA tightening notice. — [Apple news w4atic4c](https://developer.apple.com/news/?id=w4atic4c); [Apple news p6zjojqw](https://developer.apple.com/news/?id=p6zjojqw)

### Inferences
- A "TCC permissions audit" feature and any FDA-dependent feature carry platform risk within the product's first year; the architecture should isolate them behind capability checks and degrade gracefully.
- Minimum deployment target of macOS 13 (SMAppService, `setCodeSigningRequirement`) is the practical floor; arm64 native build is mandatory for longevity.

### Gaps
- No primary source located for kernel-extension policy changes in 26/27 beyond third-party FAQ claims ([MacStrategy](https://www.macstrategy.com/article.php?360=)), which I consider low reliability.
- The Tahoe "background process after quit" prompt is reported only by press, not confirmed in Apple documentation.

## 8. Apple policy risks

### Takeaway
Apple can revoke a Developer ID certificate or notarization ticket unilaterally, and has done so by mistake; revocation stops installed copies from launching. A security tool that asks for FDA and root is squarely in the category Apple is now scrutinising.

### Cited Findings
- "Any Developer ID app signed with a certificate that has been revoked can no longer be installed nor launch if it's already installed." — [Apple: Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)
- Developers cannot revoke Developer ID certificates themselves; requests go to product-security@apple.com. — [Apple: Revoking privileges](https://developer.apple.com/help/account/reference/revoking-privileges/)
- Mistaken revocation case (Aug 2020): Charlie Monroe's certificates were revoked and account suspended for about a day; Apple wrote that Downie 4 "was erroneously identified as malicious due to invalid logic in our malware detection system. This triggered the revocation of your certificate under Section 5.4 of the Developer Program License Agreement", then un-revoked it; affected users recovered "when their OCSP cache refreshes (typically within 2 hours)". — [Charlie Monroe](https://blog.charliemonroe.net/a-day-without-business/)
- Mechanics: Developer ID revocation status is served via OCSP only (checked by `trustd`), separate from the notarization check (`syspolicyd`); Apple can invalidate signatures after a timestamp cutoff, as with Panic's stolen-source incident. — [Jeff Johnson, Developer ID certificate revocation](https://lapcatsoftware.com/articles/revocation.html); [Jeff Johnson, notarization](https://lapcatsoftware.com/articles/notarization.html)
- Notarized malware and Apple's response (Aug 2020): Shlayer payloads were notarized; Apple "revoked the identified variant, disabled the developer account, and revoked the associated certificates". — [WIRED](https://www.wired.com/story/apple-approved-malware-macos-notarization-shlayer/)
- Apple's notary team Q&A (Mar 2024) says apps may be rejected even if not malicious and that Apple can revoke Developer ID certificates on request if compromise is suspected. — [Apple Developer News, 7 Mar 2024](https://developer.apple.com/news/?id=s8eigiyj) (snippet only)
- Apple CPS language for developer certificates: "Certificates may be revoked by Apple for any reason without notice to the Subscriber." — [Apple WWDR CPS v2.0](https://images.apple.com/certificateauthority/pdf/Apple_WWDR_CPS_v2.0.pdf) (WWDR CPS; the Developer ID CPS was quoted only via [lapcatsoftware](https://lapcatsoftware.com/articles/revocation.html))
- Apple's stated concern (Oct 2026): "Some developers are using Full Disk Access in ways that could put users at risk... without users' full knowledge and understanding." — [Apple Developer News](https://developer.apple.com/news/?id=p6zjojqw)

### Inferences
- Mitigations: keep the Account Holder credentials and API keys tightly held (a compromised key that notarizes malware gets the whole account disabled); never download and execute un-notarized code in an updater; state clearly in-app what FDA and the root helper are used for; avoid private APIs where a public route exists; keep a support runbook for a mistaken revocation (contact Developer Support, expect hours to a day).
- Behaviours that resemble malware heuristics (killing security processes, mass deletion, modifying TCC, disabling launchd items silently) should always be user-initiated, logged and reversible (quarantine folder with restore).
- Use Sparkle or similar only with EdDSA-signed, notarized updates so the app's own update channel does not become the "innocent app then malicious update" pattern Apple's critics describe.

### Gaps
- I found no documented case from 2024 to 2026 of Apple revoking a legitimate Mac security vendor's Developer ID or notarization; absence in my searches is not proof none exists.
- The current Apple Developer Program License Agreement text (section numbers for Developer ID revocation) was not read directly.
- No Apple-published "guidelines for security vendors" document was found beyond the entitlement request process and the notarization rules.
