## 1. Cloud path: thin proxy architecture, hosting options, Anthropic pricing, cost per analysis, caching/batch, rate limits

### Takeaway
At Nov-2026 list prices one analysis (3–10k input, 2–4k output tokens) costs roughly US$0.001–0.003 on Claude Haiku 5.5, US$0.03–0.06 on Sonnet 5.5, US$0.05–0.12 on Opus 5.5 and US$0.10–0.24 on Fable 5.2, so output tokens and model tier dominate, while prompt caching matters little at this prompt size. A thin proxy is cheap to host anywhere (Cloudflare Workers from US$5/mo, Supabase from the free/Pro plan, Railway US$5/mo, Vercel Pro US$20/mo); the real design work is abuse control, the Anthropic monthly spend cap (US$500 on the Start tier) and making sure no layer logs payloads.

### Inferences
- Cost per analysis, no caching, list prices of 2026-11-12 (low = 3k in / 2k out; high = 10k in / 4k out). Haiku 5.5: $0.0013–$0.003. Sonnet 5.5: $0.026–$0.06. Opus 5.5: $0.052–$0.12. Fable 5.2: $0.104–$0.24. Haiku 4.5: $0.013–$0.03. Batch halves each figure.
- These assume the 2–4k output includes thinking tokens. On Opus 5.5 and Fable 5.2 thinking cannot be turned off, so real output usage may exceed visible output; measure with real requests and set `effort` deliberately before fixing a price.
- Output is 67–77% of cost in every scenario, so limiting explanation length and effort saves more than trimming input.
- Caching a 2k-token system prompt on Sonnet 5.5 saves about $0.004 per call (2k × ($2 − $0.10)/1M), under 15% of the low-scenario cost. Worth enabling, but not a pricing lever. Cache TTL is 5 minutes by default, so with sparse traffic across users hits will be rare unless the 1-hour TTL is used.
- Batch (50% off) fits only non-interactive flows (e.g. scheduled weekly re-scan), and batch is not ZDR-eligible with 29-day retention (see section 2), which weakens a privacy claim.
- The Start-tier $500/month cap is a hard commercial ceiling: at Sonnet 5.5 high-scenario cost that is ~8,300 analyses/month; at Opus 5.5, ~4,100; at Haiku 5.5, ~166,000. A launch spike can exhaust it and pause the whole product until the 1st of the month, so a tier increase should be requested before launch and the proxy needs a global budget breaker.
- Rate limits (4,000 RPM on Start) are not the binding constraint for a solo product; the spend cap and the unpublished Evaluation-tier limits for a brand-new organisation are.
- Thin-proxy reference shape that follows from the cited facts: app → HTTPS → edge function that (1) validates a license/device token, (2) checks a per-license counter (daily/monthly quota) and a global budget counter, (3) enforces max input size and a fixed server-side system prompt and model (client cannot choose model or system prompt, otherwise the endpoint is a free general-purpose Claude proxy), (4) streams the Anthropic response back, (5) logs only metadata (license hash, token counts, status). Payload logging must be disabled at every layer: function console logs, platform request logs, and any AI gateway (Cloudflare AI Gateway logs payloads by default).
- Hosting fit: Cloudflare Workers is the best match for an I/O-bound streaming proxy (no duration limit or charge, CPU-time billing, $5/month, no egress fees). Supabase Edge Functions work and bring Postgres/Auth for license tables in one place, but the 150 s idle timeout and 2 s CPU limit must be respected (stream early). Vercel is viable but Hobby cannot be used commercially, so the floor is $20/month. Railway gives a normal long-lived container (simplest for arbitrary runtimes) at $5/month but with cold-start 502s in serverless mode.
- A gateway product (Vercel AI Gateway, Cloudflare AI Gateway) adds another processor/sub-processor to the privacy chain; calling `api.anthropic.com` directly from the proxy keeps the chain to hosting provider + Anthropic.

### Gaps
- Evaluation-tier limits and any deposit/credit-purchase requirements for a new Anthropic organisation are not on the rate-limits page; I found no published numbers.
- Minimum cacheable prefix length per model (Anthropic's reference says 512–4,096 tokens, model-dependent) was not verified on the live prompt-caching page.

## 2. Anthropic commercial terms for a reseller-style consumer app: retention, ZDR, training, usage policy, refusals

### Takeaway
Anthropic's Commercial Terms explicitly allow using the API "to power products and services Customer makes available to its own customers and end users", bar training on customer content, and make Anthropic the processor under its DPA; standard API retention is stated as deletion within 30 days, with ZDR by sales arrangement only and unavailable on the Fable/Mythos models. A defensive security-explanation use case is within the Usage Policy, but real-time cyber safeguards can refuse requests (HTTP 200 with `stop_reason: "refusal"`), so the app needs a designed fallback.

### Inferences
- The product is not "reselling the Services" in the plain sense if the user buys a diagnostics app whose feature happens to be powered by Claude with a fixed prompt; an open pass-through chat endpoint would look much more like resale. The line is contractual, so **[LAWYER]** should confirm, and the reported phrase "not for consumer use" needs reading in context (it most likely means the contracting customer is a business, not that end users cannot be consumers, given A.1).
- The founder is the Anthropic "Customer" and controller; end users never contract with Anthropic. That is the opposite of BYO-key, where the user holds the provider relationship (as Raycast states for BYOK).
- A truthful privacy statement at standard terms is "our AI provider deletes inputs and outputs within 30 days and does not train on them; flagged content may be kept up to 2 years". "Zero retention" can only be claimed after a ZDR agreement, only for non-Fable models, never for batch, and still with the flagged-content exception.
- Since ZDR is sales-gated, a solo founder may not get it; choosing Sonnet/Opus/Haiku 5.5 rather than Fable keeps the option open.
- Security content is precisely what cyber classifiers watch. Script excerpts from real malware or persistence items may trigger refusals even though the use is defensive. Design: check `stop_reason` before parsing, fall back to another model or to a deterministic local explanation ("could not be analysed by AI; here is the rule-based finding"), and never surface a refusal as "safe". Applying to the Cyber Verification Program is the documented route if refusals are frequent.
- Flagged requests retained for up to 2 years will contain user-device data; the privacy policy should say so.
- Do not put any user data in JSON schemas for structured output (schemas are cached up to 24 h outside message-content protections).

## 3. On-device path on macOS: Apple Foundation Models, MLX / llama.cpp, quality gap, hybrid routing

### Takeaway
Apple's on-device model (about 3B parameters, 4,096-token window per session covering input and output, guided generation with guaranteed structure, Apple Intelligence hardware and settings required) is free and private but, in Apple's own words, "not designed for world knowledge or advanced reasoning"; it can phrase explanations for single findings but cannot ingest a 3–10k-token findings bundle. Bundled open models via MLX or llama.cpp run at roughly 20–30 tok/s for 4-bit 8B-class models on 16 GB Macs and need 5–7 GB of memory, which is hard to justify inside a product that diagnoses slow Macs; 8 GB Macs are limited to 3–4B models.

### Cited Findings

**Apple Foundation Models framework**
- "The on-device model we just used is a large language model with 3 billion parameters, each quantized to 2 bits." "It is optimized for use cases like summarization, extraction, classification, and many more. It's not designed for world knowledge or advanced reasoning, which are tasks you might typically use server-scale LLMs for. Device scale models require tasks to be broken down into smaller pieces." — [WWDC25 session 286](https://developer.apple.com/videos/play/wwdc2025/286/)
- "All of this runs on-device, so all data going into and out of the model stays private. That also means it can run offline! ### Inferences
- A 3–10k-token findings bundle plus 2–4k output does not fit a 4,096-token session. On-device Apple use would need one session per finding with a very short instruction block and schema, and would lose cross-finding reasoning (prioritisation across the whole machine), which is the product's highest-value output.
- Speed estimate for a bundled 8B model on a 16 GB Mac: 3k tokens out at ~25 tok/s is ~2 minutes of generation plus prefill (a 4K prompt took 16–20 s to first token on an M2 Air). On 8 GB Macs a 4B model would be faster to generate but weaker, and a 5 GB model would put the machine into memory pressure. For a tool whose promise is diagnosing slowness, loading 3–7 GB into unified memory during a scan is a product contradiction; Apple's system model avoids the download and is managed by the OS but still needs Apple Intelligence enabled.
- The available evidence consistently points the same way: small models are usable for bounded classification/phrasing inside a rule-governed pipeline, and unreliable as sole judges (missed attacks, fabricated evidence, higher injection success). Even frontier models over-flag benign items, so plausibility verdicts need deterministic rules around them regardless of where the model runs.
- Hybrid routing pattern consistent with the above: (a) deterministic rules decide severity floors and known-good allowlists; (b) on-device Apple model, when available, writes plain-language explanations per finding with `@Generable` output, used for free tier / offline / "nothing leaves my Mac" mode; (c) cloud model handles the whole-machine prioritisation and ambiguous findings for paying users who opted in; (d) every tier fails safe to rule-based text. This also gives a truthful privacy story per tier.
- macOS 27's unified Swift API for on-device and server models reduces client code for a hybrid, but a server model still needs credentials, so it does not remove the need for the proxy.
- Model behaviour changes with OS updates (three model versions already), so on-device prompts need regression evals per OS release.
- Core ML is the route for small classifiers (e.g. a fine-tuned benign/suspicious text classifier), not for generative explanation; I did not find a source making this case specifically for this product type, so treat it as a design judgement.

## 4. Prompt-injection risk with attacker-controlled strings; mitigations for a no-tools, structured-output design; evaluating verdict quality

### Takeaway
The no-tools, schema-constrained design already follows the strongest published principle (untrusted input must not be able to trigger consequential actions), which reduces injection impact to a manipulated verdict or misleading text shown to the user. Prompt-level defences such as delimiting or spotlighting are worth adding but are proven bypassable (>90–95% success under adaptive attack), so severity floors and "may the model close this?" rules must live in ordinary code, and verdict quality must be measured on a labelled set including injected samples.

### Cited Findings
- Guiding principle: "once an LLM agent has ingested untrusted input, it must be constrained so that it is impossible for that input to trigger any consequential actions"; outputs "should not pose downstream risks — such as exfiltrating sensitive information (e.g., via embedded links) or manipulating future agent behavior (e.g., harmful responses to a user query)" — [Design Patterns for Securing LLM Agents against Prompt Injections](https://arxiv.org/html/2506.08837v3)
- Relevant patterns from the same paper: action-selector (model chooses from a fixed list), quarantined/dual LLM where the tool-less model's output "must satisfy certain safety constraints", map-reduce where the reduce step is non-LLM or the map output is constrained (e.g. "a regex that ensures the output of map is a number"), and context minimisation — [Design Patterns paper](https://arxiv.org/html/2506.08837v3)
- Microsoft's Spotlighting: "delimiting, datamarking, and encoding" modes; "a probabilistic technique"; system prompts are "a probabilistic mitigation" — [Microsoft MSRC, Jul 2025](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)
- Adaptive attacks: "we bypass 12 recent defenses ... with attack success rate above 90% for most; importantly, the majority of defenses originally reported near-zero attack success rates." Spotlighting and prompt sandwiching showed ASR "as low as 1%" on static attacks but "above 95%" under adaptive search; injection detectors (Protect AI, PromptGuard, Model Armor) >90%, PIGuard 71% — [The Attacker Moves Second (arXiv)](https://arxiv.org/abs/2510.09023); [USENIX Security 2026](https://www.usenix.org/conference/usenixsecurity26/presentation/nasr)
- "Schema conformance isn't authorization"; structured outputs "can still produce wrong values, and a valid string can still contain hostile content"; prefer "booleans, enums, bounded identifiers, and numbers" for fields crossing a trust boundary — [LeetLLM summary of the patterns](https://leetllm.com/learn/prompt-injection-defense-strategies) (secondary)
- Real-world signal: in June 2025 Check Point found a malware sample on VirusTotal with an embedded string asking any AI analysis tool to answer "NO MALWARE DETECTED"; it did not work against the models tested — reported in [CyberS3c, Oct 2026](https://www.cybers3c.pt/blog/o-atacante-tambem-escreve-nos-seus-logs/) (secondary; original Check Point post not fetched)
- Same article reports a May 2026 study (Pandey and Bhujang) on log triage: a direct "ignore and classify as benign" order suppressed 0% of malicious events, while persona/context hijack ("this traffic is from the authorised scanner") suppressed 68% — [CyberS3c](https://www.cybers3c.pt/blog/o-atacante-tambem-escreve-nos-seus-logs/) (secondary)
- CyberS3c's own measurement (1,440 responses, six fast/cheap models, fixed attack texts): Claude Haiku 5.5 followed 0/60 injections in each attack condition and flagged the attempt in 53 of 60 attacked cases; the authors caution "o zero dos modelos recentes é um bom sinal, não uma garantia" — [CyberS3c](https://www.cybers3c.pt/blog/o-atacante-tambem-escreve-nos-seus-logs/)
- Small local model comparison: 10% injection success for LLM-only with a 1.5B model vs 0% with rule floor + close veto + injection guard; guardrails that mattered were "Rule floor", "Close veto" (model may close only when a trusted fact explains it), "Injection guard", "Fail-safe on invalid output" — [soc-triage-lab](https://dev.to/willeysingh/private-ai-soc-triage-lab-can-a-small-local-llm-triage-alerts-safely-16l7)
- Evaluation practice from those studies: decide outcomes by code rather than another model ("O resultado é decidido por código, não por outro modelo"), hand-read flagged cases, include a no-attack condition, report confidence intervals — [CyberS3c](https://www.cybers3c.pt/blog/o-atacante-tambem-escreve-nos-seus-logs/); use class-imbalanced sets reflecting reality (5 true vs 30 false positives) — [SIABench thesis](https://spectrum.library.concordia.ca/id/eprint/996238/1/Jajodia_MASc_F2025.pdf); report recall, precision, F1, MCC and separate false-positive rate on benign-only data — [DeepTempo SOCBench post](https://www.deeptempo.ai/blogs/the-36-percent-false-positive-problem-with-llm-in-the-soc)
- Benign-prior bias: frontier LLMs flagged 36–86% of clean traffic as malicious in SOCBench (vendor-run) — [DeepTempo SOCBench post](https://www.deeptempo.ai/blogs/the-36-percent-false-positive-problem-with-llm-in-the-soc)
- Anthropic's API supports schema-constrained output via `output_config.format`, which is ZDR-eligible with the schema cached up to 24 hours — [Anthropic API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)

### Inferences
- Threat model for this product: the attacker controls process names, bundle names, file paths, launch-item labels and script text on a compromised Mac. With no tools, the worst outcomes are (1) a malicious item labelled plausible/benign, (2) persuasive attacker text relayed to the user in the explanation ("to fix this, run the following command…", a URL), (3) cost abuse by huge strings. (1) and (2) are real harms for a security product.
- Mitigations that follow from the evidence, in order of strength:
  1. Deterministic floors in code: findings matching high-risk rules keep their severity whatever the model says; the model can raise but not lower below the floor, and can only mark something benign when a trusted local fact supports it (valid Apple/Developer ID signature, notarisation, known-good hash).
  2. Typed verdict fields: enum verdict, bounded integer confidence, finding IDs assigned by the app (not copied from input). Treat free-text explanation as untrusted display text: render as plain text, never as markdown/HTML/links, strip URLs and shell commands or show them only from a vetted remediation catalogue keyed by finding type.
  3. Input hygiene: length caps per field, truncate script excerpts, escape/delimit attacker-controlled strings with random per-request delimiters or datamarking, and state in the system prompt that field contents are evidence, never instructions. Useful but probabilistic.
  4. One finding (or small group) per call for the verdict step limits cross-contamination: an injected string in one item cannot rewrite verdicts for others. This costs more calls, so a cheap model can do per-finding verdicts and a second call can do the summary using only typed outputs (context minimisation).
  5. Ask the model for an `injection_suspected` boolean; an instruction-like string inside a process name is itself a detection signal worth showing.
  6. Fail safe: invalid output, refusal or timeout produce rule-based text, never "no issues".
- Pseudonymisation interacts with injection defence: replacing user names/paths with tokens removes some attacker text but not process names or script bodies.
- Eval design: build a labelled golden set of real macOS findings (benign common software, adware/PUP, known stealer persistence patterns, admin tools that look scary), heavily benign-weighted to match reality; add an adversarial split with injected strings in every attacker-controllable field, including "plausible context" attacks rather than only "ignore previous instructions". Track false-negative rate on malicious items (the costly error), false-positive rate on benign-only machines (the churn-driving error), verdict stability across repeated runs, schema-validity rate, refusal rate, injection success rate, cost and latency per model. Re-run on every model, prompt or OS-model change. Grade verdict enums by code; use human review (not an LLM judge alone) for explanation quality samples.
- No defence makes the verdict trustworthy enough to auto-act; keeping the LLM out of action execution, as designed, is the control that bounds the damage.

## 5. Privacy law: LGPD, GDPR, US state law; roles, bases, transfers, DPIA/RIPD, rights, children; consent UX

### Takeaway
Locally pseudonymised device and security data sent through the founder's proxy is still personal data for the founder as controller under both the EDPB's and the CJEU's reading (the founder can link it to a license or account), so LGPD and GDPR apply in full, with Anthropic as processor under its DPA. EU–Brazil transfers are covered by mutual adequacy since January 2026, but the onward transfer to Anthropic in the US still needs a transfer mechanism (EU SCCs via the DPA for EU data; ANPD standard clauses for Brazilian data), and the mix of emerging technology with scale points toward doing a RIPD/DPIA. CCPA is unlikely to apply at solo-founder scale.

### Cited Findings

**Is pseudonymised data personal data?**
- EDPB Guidelines 01/2025 (adopted 16 January 2025): "Pseudonymised data, which could be attributed to a natural person by the use of additional information, is to be considered information on an identifiable natural person, and is therefore personal. This statement also holds true if pseudonymised data and additional information are not in the hands of the same person." — [EDPB Guidelines 01/2025](https://www.edpb.europa.eu/system/files/2025-01/edpb_guidelines_202501_pseudonymisation_en.pdf)
- EDPB: "Pseudonymisation can reduce risks and make it easier to use legitimate interests as a legal basis (Art. 6(1)(f) GDPR), as long as all other GDPR requirements are met." — [EDPB press release](https://www.edpb.europa.eu/news/edpb-adopts-pseudonymisation-guidelines-and-paves-the-way-to-improve-cooperation-with_en)
- CJEU, EDPS v SRB, C-413/23 P (4 September 2025): "pseudonymised data must not be regarded as constituting, in all cases and for every person, personal data ... in so far as pseudonymisation may, depending on the circumstances of the case, effectively prevent persons other than the controller from identifying the data subject" (para 86); but identifiability for the information duty "must be assessed at the time of collection of the data and from the point of view of the controller" (para 111) — [CJEU C-413/23 P](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A62023CJ0413)
- Pending change: the Commission's Digital Omnibus (COM(2025) 837, 19 Nov 2025) would amend the Art. 4(1) definition along the SRB line; as of 9 Nov 2026 the Council's position keeps the definition and adds an Article 25a; the same data "may be personal data for one organization (including the controller and its processors) but not for an independent recipient" — [Lewis Silkin, 9 Nov 2026](https://www.lewissilkin.com/insights/2026/11/09/digital-rulebook-simplification-of-eu-data-protection-and-cyber-rules-102o7e4); [Redactic, Oct 2026](https://redactic.eu/blog/pseudonymisation-anonymisation-edpb-guidelines-02-2026-srb/)

**GDPR scope, basis, representative**

- ECA Digital (Lei nº 15.211, 17 Sept 2025) applies to IT products/services "direcionados a crianças e a adolescentes ou de acesso provável por eles", imposing prevention, protection, information and security duties; app stores and operating systems must assess age and provide an age signal via API (art. 12); the federal government published its regulation in March 2026 and ANPD has issued a scope guide — [Lei 15.211/2025](https://www2.camara.leg.br/legin/fed/lei/2025/lei-15211-17-setembro-2025-797997-normaatualizada-pl.pdf); [Planalto Q&A, Mar 2026](https://www.gov.br/planalto/pt-br/acompanhe-o-planalto/noticias/2026/03/governo-do-brasil-regulamenta-o-eca-digital-novo-marco-na-protecao-de-criancas-e-adolescentes-na-internet/18032026_perguntas_respostas_eca-digital.pdf/@@download/file); [ANPD ECA Digital](https://www.gov.br/anpd/pt-br/assuntos/eca-digital)

**US**

### Inferences
- Roles: founder (Brazilian entity) = controller for Brazilian, EU and US users; Anthropic = processor (operador) under the DPA; hosting provider = processor; payment/license provider = separate chain. With BYO-key the user contracts with Anthropic directly, which is one reason BYO-key was legally lighter than the commercial design will be.
- Personal-data status: process names, file paths (often containing the user name), installed apps and launch items tied to a license key or device ID are personal data for the founder even after local pseudonymisation, because the founder can link the request to a customer. Under SRB the same payload may arguably not be personal data for Anthropic if Anthropic cannot reasonably re-identify, but that does not relieve the controller, and the law is in flux (Digital Omnibus). Stronger pseudonymisation plus a proxy that does not forward license IDs to Anthropic and does not log payloads improves the risk position and the legitimate-interest balancing. **[LAWYER]**
- Installed software can incidentally reveal sensitive categories (health apps, religious or sexual-orientation-related apps, VPN/activist tools). Legitimate interest is unavailable for sensitive data under LGPD, so either filter such signals locally or rely on consent for the AI upload. **[LAWYER]**
- Legal basis options for the cloud-AI step: (a) performance of contract where AI analysis is the purchased feature; (b) legitimate interest supported by GDPR Recital 49 for security services plus pseudonymisation; (c) consent. For reading information from the user's device and sending it off-device, EU ePrivacy rules on terminal-equipment access may independently require consent unless strictly necessary for the service the user requested; making the AI analysis an explicit, user-triggered, opt-in action is the conservative design and matches Raycast's "only runs when you explicitly trigger it" pattern. **[LAWYER]**
- Transfers: EU user → Brazil is covered by adequacy since Jan 2026. EU user → Anthropic US: SCCs in Anthropic's DPA. Brazilian user → Anthropic US: needs an LGPD art. 33 mechanism; the ANPD standard clauses had to be in place by Aug 2025 for clause-based transfers, and they cannot simply be assumed to be in Anthropic's DPA. If the proxy is hosted outside Brazil (US/EU edge), that is a transfer too. **[LAWYER]** to confirm mechanism and whether a transfer impact assessment is expected.
- RIPD/DPIA: generative AI plausibly counts as "tecnologias emergentes ou inovadoras"; if the user base becomes large, the art. 4 high-risk test is met and the small-agent simplifications fall away. Because legitimate interest also exposes the controller to an ANPD request for a RIPD, preparing a short RIPD/DPIA and a legitimate-interest assessment before launch is the low-regret path.
- Art. 27 GDPR: selling to EU consumers continuously is not "occasional", so an EU representative is probably required. **[LAWYER]**
- Rights handling is easier if the proxy stores nothing but metadata: access/deletion requests then cover license records and usage counters, and the privacy policy can state that analysis payloads are not retained by the vendor and are deleted by the AI provider within 30 days (subject to the flagged-content exception).
- Children: a Mac utility is general-audience, but Anthropic's policy treats under-18s as minors and ECA Digital covers "acesso provável"; a terms-of-use minimum age of 18 for the AI feature plus use of OS/App Store age signals where available is the simplest posture. **[LAWYER]**
- CCPA: a solo founder will be far below $26.6M revenue and does not sell or share data, so CCPA likely does not apply; other US state laws generally have similar volume thresholds (not researched individually). A clear privacy policy still serves FTC "unfair or deceptive" exposure: on-device and no-retention claims must be literally true.
- Consent UX pattern that emerges from the vendors reviewed: a per-feature label of where processing happens (on-device vs cloud), a first-use screen showing exactly which fields leave the Mac (ideally a preview of the pseudonymised payload), named AI provider and retention period, explicit trigger rather than background upload, separate opt-in for any data donation or feedback, and a fully local mode.

## 6. How competitors and adjacent products disclose and architect AI features

### Takeaway
The adjacent products that are transparent about AI (Raycast, MacPaw) all use a vendor-operated backend that holds the provider keys, state plainly that prompts are not logged or stored by the vendor, name the model providers, and label features as on-device or cloud; BYO-key and local models appear as power-user options, not the default. Consumer security suites (Norton, Malwarebytes, Moonlock) bundle AI assistants into existing subscriptions rather than charging a separate AI add-on, and disclose far less about the underlying models.

### Cited Findings
- Raycast architecture: Raycast-provided models go through "secure server infrastructure to protect our API keys"; "Forward your input to the AI provider's API; Exclude any personal information when doing so; Only share the minimum necessary data"; providers are contractually barred from training — [Raycast AI privacy](https://manual.raycast.com/ai/raycast-ai-privacy-security)
- Raycast BYOK: for Anthropic, Google and OpenAI keys "Requests are processed through our servers in order to unify the model APIs"; OpenRouter and custom providers go "directly from your device"; "Custom API keys are stored locally on the user's computer, not in our backend"; "When using BYOK, you maintain the contractual relationship with the AI provider" — [Raycast AI privacy](https://manual.raycast.com/ai/raycast-ai-privacy-security)
- Raycast also supports connecting an existing Claude or ChatGPT subscription and local models via Ollama; "Raycast AI is included in paid Pro plans"; plans include monthly AI Credits, and own keys/subscriptions do not consume them. The page shows "$12/ user / month" with "$144 billed annually" for a tier including advanced models and BYOK (the tier naming in the snippet is ambiguous) — [Raycast AI](https://www.raycast.com/core-features/ai)
- MacPaw: cloud requests are "transmitted to the applicable AI model provider solely for the purpose of fulfilling Your request"; some apps use Apple's on-device `SystemLanguageModel`; "Setapp AI+" is "a managed AI gateway operated by MacPaw" routing to third-party models chosen in settings; "MacPaw is not a party to any agreement between you and an AI Model Provider" — [MacPaw AI Apps Privacy Policy](https://macpaw.com/legal/ai-apps-privacy-policy); [MacPaw AI integrations](https://macpaw.com/legal/ai-apps-third-party-integrations)
- Moonlock (MacPaw) lists an "AI-powered Scam Detector" that "Uses AI to check pasted messages for phishing patterns" alongside malware protection, VPN and a Security Advisor — [Macworld Moonlock guide, Oct 2026](https://www.macworld.com/the-macpaw-moonlock-guide-to-mac-security) (appears to be partner content)
- Malwarebytes Scam Guard is "your built-in AI-powered chat companion available within Malwarebytes Premium Security for Windows, Mac, iOS, and Android"; the bot "analyzes the text for potential security threats, cross checks with our protection databases" — [Malwarebytes AI Hub](https://www.malwarebytes.com/ai-hub); [Malwarebytes help](https://help.malwarebytes.com/hc/en-us/articles/43279273238555-Detecting-threats-with-Scam-Guard-on-Desktop-Security)
- Malwarebytes also distributes through the model vendor's surface: "Malwarebytes in ChatGPT" (Feb 2, 2026) gives ChatGPT users verdicts "powered by Malwarebytes' continuously updated threat database" — [Malwarebytes press release](https://www.malwarebytes.com/press/2026/02/02/malwarebytes-makes-chatgpt-smarter-about-scams-malware-and-online-risk)
- Norton Genie is presented as "your AI-powered assistant" inside plans "now packed with AI-Powered Scam Protection"; listed (promotional) plan prices on the page start at $59.99 for one device; the description cites NLP and machine learning "trained on millions of scam attempts" without naming an LLM vendor — [Norton AI scam protection](https://us.norton.com/feature/ai-scam-protection)

### Inferences
- The pattern for a credible privacy-first position is specific and checkable statements: who the provider is, what is sent, what the vendor stores (metadata only), the provider's retention window and exceptions, and what stays on-device. Raycast even documents the Fable 30-day exception, which shows users of this category tolerate nuance when it is disclosed.
- None of the security suites reviewed sells AI as a separately priced add-on; AI is a retention/positioning feature inside the subscription. Raycast is the clear example of metering (credits) with BYOK as the escape valve. For a low-priced Mac utility, a quota included in the license plus optional BYO-key for heavy users mirrors both models and caps cost exposure.
- Keeping BYO-key as an "advanced" option has a second benefit: for those users the contractual and data relationship is between the user and Anthropic, as Raycast states.
- Security vendors combine the LLM with their own threat-intelligence lookup and present the verdict as coming from the database, with the model as the conversational layer. That matches the rule-floor design in section 4.
- Competitors' assistants focus on scam/phishing content the user pastes in; an LLM that explains findings from a system scan is a less crowded position, but it sends more device-derived data, so the disclosure bar is higher than for Scam Guard-style features.
